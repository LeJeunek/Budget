# Product Spec — Phase 5b: Motion & Craft

This document covers Phase 5b only — Motion & Craft, the second and final sub-phase of Phase 5, gated behind Phase 5a's (Accessibility & Responsive Foundation) own review gate, which passed on its second Release Manager pass (`docs/release/phase-5a-second-pass.md`, APPROVE, no open functional gaps). Per the CTO's Phase 5 kickoff pass (`docs/planning/roadmap.md`, "Phase 5 CTO kickoff pass," 2026-07-30, Section 1's dependency-chain reasoning), this spec is written against 5a's now-final, now-audited DOM structure — the bottom navigation, `ResponsiveDataTable`/`DataTableCardList` mobile card-list fallback, the Calendar v2 condensed-grid-plus-`DayDetailSheet` day-detail pattern, and every ARIA/landmark/focus fix 5a's structural pass made — not against the pre-5a app shape. It is a **product** spec: it does not design the shared reduced-motion utility, the expandable-card primitive's file/prop boundary, or the page-transition wrapper's composition point in the app shell — those are the Solution Architect's and UI Component Engineer's calls, per the CTO's own Section 6 milestone 3.

Every acceptance-criteria bar cited below as "CTO-set" comes from the kickoff pass's Section 3 ("Motion & Craft (5b)") and is binding, not a Product Owner suggestion — restated here so an implementing agent never has to reconstruct it from `roadmap.md`. Where the kickoff pass named a constraint without a concrete number or an exhaustive per-screen scope (e.g. chart-transition duration, which screens get number counters, what "expandable cards" concretely means beyond the one ad hoc instance that exists today), this spec supplies that concreteness directly — the same "flesh into full acceptance criteria per screen/component" role 4a's spec played for the CTO's structured-output/data-minimization constraints. See "Open Questions Resolved by This Spec" below for each such call, stated explicitly rather than left implicit.

## User Story

As a FinanceOS user, I want the numbers, charts, page changes, and expandable detail I interact with every day to feel considered and alive — a balance updating with a visible count rather than an instant jump-cut, a chart drawing itself in rather than popping into existence, a page change that doesn't feel like a hard reload, a card that reveals more detail with a motion cue instead of an abrupt layout snap — **without that polish ever costing me usability**: if my operating system tells every app on my device I don't want motion, FinanceOS is one of the apps that actually listens, instantly, everywhere, with no animation ever the only way information reaches me.

## Business Value

Every phase through 5a added financial substance, personalization, or structural correctness; this phase adds none of those — it is the last, purely presentational layer, the "software someone would pay for" bar the original Phase 5 stub named and 5a's own spec already noted is not independently verifiable as prose (`phase-5a-accessibility-responsive.md`'s Business Value section makes the identical point about its own stub language). Concretely:

- **This is the payoff phase for 5a's investment, not a parallel workstream.** 5a's entire purpose, per the CTO's own dependency-chain reasoning, was to finalize the DOM/interaction structure motion would be built against — the bottom nav, the five `DataTableCardList` consumers, the Calendar v2 condensed grid and `DayDetailSheet` — so that this phase's animation work is built once, against final structure, rather than redone when a later structural change reshapes the markup underneath it. Shipping 5b correctly is what makes 5a's own cost (a full accessibility/responsive audit pass across 24 routes) pay off as durable investment rather than partially wasted effort.
- **Motion is legitimate craft signal for a product whose stated ambition is professional-grade personal finance software, but only when it never trades away the usability 5a just finished securing.** A number that visibly counts up communicates "this changed, and by how much" more legibly than an instant jump — genuinely useful information, not just decoration, for a product about tracking money over time. But this value is real only if it never regresses what 5a shipped: a `prefers-reduced-motion` user, a keyboard user, a screen-reader user, and a mobile user (5a's four audiences) must all get a version of every 5b feature that works exactly as well for them as the version without motion would.
- **`prefers-reduced-motion` is the one binding requirement this phase cannot treat as optional polish.** The kickoff pass is explicit that every animation this phase adds must have an instant-state-change fallback — not a nice-to-have accessibility add-on, but the same class of hard requirement 5a's WCAG 2.1 AA floor was. A user with vestibular sensitivity who has already told their OS "no motion, anywhere" is exactly the user this phase's own decoration must never silently exclude — the identical "cannot afford to silently exclude" framing 5a's Business Value section used for keyboard- and screen-reader-only users, applied here to motion specifically.
- **This closes the roadmap's original three-bullet Phase 5 stub in full.** Once this phase's review gate passes, every workstream the stub named — motion/transitions, accessibility, responsive/mobile — is shipped, audited, and signed off, closing out Phase 5 in its entirety.

## Capability: Reduced-Motion Foundation

This capability is not one more surface alongside the other four — it is a binding precondition every other capability below is built against, restated here as its own capability because the kickoff pass itself gives it that same weight ("a binding requirement of every animation this phase adds, not optional polish").

### Acceptance Criteria

1. **OS-level `prefers-reduced-motion: reduce` is respected app-wide, implemented once, centrally** (CTO-set: "e.g. `MotionConfig reducedMotion="user"` at the app shell, or an equivalent single shared utility") — never a per-component ad hoc check reimplemented by each of this phase's four other capabilities.
2. **No persisted in-app override of any kind ships in this phase or any other** — restated from 5a's own already-final resolution (`phase-5a-accessibility-responsive.md`, Open Questions Resolved (a)): OS-level `prefers-reduced-motion` is the complete, correct mechanism on its own terms, not a partial one a second in-app toggle would need to complete. No new `UserPreference` field. This is settled, not re-litigated here.
3. **When active, every animation in scope (all four other capabilities below, plus the two motion instances that already existed in this codebase before this phase — `components/shared/progress-ring.tsx`'s SVG stroke animation and `components/ui/progress.tsx`'s transform-based fill) renders its end state immediately** — no interpolation, no "shorter" version of the same animation, an instant state change exactly as the CTO's own wording requires. This phase's job on those two pre-existing components is bringing them under this same central mechanism, not rebuilding either from scratch.
4. **The preference is honored reactively, not just at initial page load** — if a user changes their OS-level reduced-motion setting while FinanceOS is open in a tab (a standard `matchMedia` change event, not a page reload), every subsequently-triggered animation in the app respects the new setting immediately, without requiring a manual refresh.
5. **No animation is ever the sole means information is conveyed** — restated from 5a's identical "never color alone" discipline (Accessibility AC8), applied here to motion: a number counter's *final* value, a chart's *final* rendered data, and an expandable card's *final* expanded/collapsed content must each be fully legible and correct with the animation entirely absent (reduced motion) or interrupted (e.g. a user navigating away mid-count) — the animation is always decoration on top of an already-complete, already-correct static end state, never a required step to reach it.

### Edge Cases

- **A user's `prefers-reduced-motion` setting is `reduce` for their very first page load of a session** (never toggled mid-session): every one of this phase's animations must render instantly from the first paint — this is the default-off state for that user, not a state the app "transitions into."
- **Automated testing environments** (Playwright, CI) commonly run with no explicit `prefers-reduced-motion` value set, which resolves to `no-preference` by default — this phase's test coverage must explicitly emulate `reduce` (Playwright's `page.emulateMedia({ reducedMotion: "reduce" })`) rather than relying on incidental CI-environment defaults, so the reduced-motion path is genuinely exercised, not accidentally always skipped.
- **A component that has both a Framer-Motion-driven animation and an unrelated CSS `transition-colors` hover state** (e.g. a button that is also a number-counter's container): reduced motion suppresses the Framer Motion animation only — ordinary hover/focus CSS transitions (the CTO's own "simple state changes" category) are explicitly out of this capability's scope and continue to function normally, since they are not the class of motion `prefers-reduced-motion` users are asking to have suppressed under this project's own tool-fit distinction (CTO Section 3's "CSS transitions... remain the default for simple hover/focus state changes").

## Capability: Number Counters

### Acceptance Criteria

1. **Every headline currency or percentage figure produced through the `formatCurrency`/`useFormatCurrency` pipeline (Phase 4c) — application-wide, regardless of which shared component, if any, renders it — animates from its previously-rendered value to its new value**, on (a) initial mount, and (b) any subsequent update where the underlying number itself changes — never re-triggered by an unrelated parent re-render (a sibling card's own state change, a theme toggle, a route-level revalidation that leaves this particular value unchanged). This capability's applicability is defined by the formatting pipeline a figure flows through, not by which component happens to render it today: `components/shared/stat-card.tsx`'s `value` prop and `components/shared/progress-ring.tsx`'s default percentage label are the two components that already exist for this purpose, but a headline figure rendered as a plain `formatCurrency`-driven `<span>` outside either of those two components is equally in scope, provided it clears the "headline, not row-level" bar this capability's own AC7 already draws. "Headline" vs. "row-level" remains a per-surface distinction, decided by AC7's reasoning, never a per-component one — see "Open Questions Resolved by This Spec," item 3, for why this capability's mechanism is defined this way rather than by component.
2. **Duration bounded 300–600ms** (CTO-set range), one shared value used consistently everywhere this capability applies — not tuned per screen or per consumer.
3. **The animated, in-flight intermediate value is rendered through the exact same `formatCurrency`/`useFormatCurrency` pipeline as the final, settled value** — never a second, parallel formatting path (a raw `.toFixed(2)`, a hand-rolled thousands separator, or any other bespoke number-to-string logic during the tween) for the animated number specifically. This is the CTO's single most emphasized 5b constraint, given 4c's currency-display fix just finished wiring that one pipeline app-wide — restated here as non-negotiable.
4. **Percentage figures get the identical counting treatment as currency figures** — goal/budget/debt-payoff progress percentages and the Financial Health Score's numeric score are not a separate, second animated-number behavior; one consistent counting treatment covers both currency and percentage headline figures app-wide.
5. **Reduced motion:** instant snap to the new value, still rendered through the same formatting pipeline (AC3 holds even with the animation itself suppressed).
6. **Concrete in-scope surfaces** (every route/component rendering a headline currency or percentage figure through the `formatCurrency`/`useFormatCurrency` pipeline, per AC1's mechanism definition above): Dashboard (`/`, stat cards + Financial Health Score ring), Accounts (`/accounts`, balance figures), Budgeting (`/budgeting`, category-row progress + summary cards), Goals and Financial Goals (`/goals`, `/financial-goals` + both detail routes, progress rings/bars and target/contributed figures), Bills (`/bills` + detail, upcoming/paid amounts), Recurring Income (`/income` + detail, stream amounts), Debt (`/debt`, balance/payoff figures), Investments (`/investments` + detail, holding values/gains), Analytics (`/analytics`, its 12-metric dashboard's headline figures), Financial Health Score detail (`/financial-health-score`, the score itself plus subscores).

   Four of these ten (Dashboard, Budgeting, Goals/Financial Goals, Recurring Income) already render their headline figures through `StatCard`/`ProgressRing` today, confirmed by direct inspection. The other six (Accounts, Debt, Investments, Analytics, and both Financial Health Score surfaces — its Dashboard badge and its own detail-route breakdown) currently render their headline figures via plain `formatCurrency`-driven `<span>` elements, not `StatCard`/`ProgressRing`. That is not a reason to exclude them: AC1 above defines this capability's scope by the formatting pipeline a figure flows through, not by the specific component rendering it, and all ten surfaces named here genuinely render their headline figures through `formatCurrency`/`useFormatCurrency` — so all ten are equally, correctly in scope. See "Open Questions Resolved by This Spec," item 3, for the reasoning behind this resolution and why it does not dictate which component ultimately renders each figure.
7. **Concrete out-of-scope surfaces, with reasoning, per this AC's own systematic-pass requirement:**
   - **Transactions' table/card rows** (`/transactions`): each row's individual amount is one line among many, not a headline single figure — animating every row on every re-sort, re-filter, or page change would read as visual noise on this app's highest-interaction-frequency surface, not polish. Excluded deliberately, not by omission.
   - **Reports** (`/reports`): its figures are rendered inside generated PDFs, a static output with no live, mounted DOM number to animate — this capability applies only to interactive, in-app-rendered figures.
   - **Admin** (all six `/admin/*` routes): Admin's own data (user counts, audit-log timestamps, feature-flag states) is operational/internal, not this product's financial data — no currency or percentage headline figure exists there to animate, consistent with 5a's own lighter-touch precedent for Admin.

### Edge Cases

- **A value updates to the identical value it already held** (e.g. an unrelated revalidation returning an unchanged amount): no animation replays — this is the directly testable form of AC1's "never re-triggered by an unrelated re-render."
- **A value transitions to/from `null`/`undefined`** (e.g. a goal's optional planned monthly contribution being cleared): no numeric interpolation is attempted from or to a non-numeric state; the display falls back instantly to whatever `formatCurrency`'s own existing null-handling renders (e.g. an em dash), consistent with AC3.
- **A value crosses zero** (e.g. a debt balance being paid down to zero and continuing negative, an account going overdrawn): the counter interpolates numerically through zero exactly as through any other value; any sign-dependent visual treatment (e.g. red for negative) switches at the exact moment the underlying value crosses zero, not before or after.
- **A single update changes the value by a very large amount** (e.g. importing a large batch of transactions that shifts a category total substantially in one revalidation): duration stays within the fixed 300–600ms bound regardless of the magnitude of change — a fixed-duration tween, never a fixed-speed one that would take proportionally longer for a bigger jump.
- **`StatCard`'s existing `loading` skeleton resolving to a loaded value:** this is a mount-with-initial-value case (AC1a) — the counter animates once, from its starting point (zero, or whatever the component's documented starting state is) to the loaded value, exactly like any other first-mount case, not treated as a second, special "loading" behavior.

## Capability: Chart Transitions (Recharts + the Analytics heatmap)

### Acceptance Criteria

1. **Every Recharts-rendered chart in the inventory gets a bounded, consistent entrance animation on mount/data-load, and an equally bounded update animation on subsequent data changes without a full remount** (a period-selector change, a transaction edit that changes a category total) — matching the CTO's "entrance/update" wording verbatim. Concrete duration bound: **400–800ms**, one shared value used consistently across every chart — this spec's own supplied number, since the CTO's Section 3 constraint says "bounded, consistent duration" for charts without fixing a figure the way it explicitly did for number counters (300–600ms); see "Open Questions Resolved" below for the reasoning behind this specific range.
2. **Zero layout shift (CLS):** each chart's container reserves its final dimensions before data loads and before/during its entrance animation — the animation happens to the chart's internal content (bars growing, a line drawing in, donut segments sweeping in), never to the container's own size.
3. **Recharts' own native per-chart animation props are the mechanism for this capability, not a Framer Motion reimplementation of what the charting library already does** — most Recharts primitives already expose `isAnimationActive`/`animationDuration`/`animationEasing`; this phase's job is largely wiring a shared, consistent duration constant and a reduced-motion `isAnimationActive={false}` gate across every chart consumer, not building a second, competing animation system on top. This is the same tool-fit discipline the CTO's own Section 3 constraint states generally ("Framer Motion is reserved for orchestrated motion... matching each tool's actual strength") — applied here concretely: Recharts' native animation is the right tool for a Recharts chart's own internal drawing, the same way a plain CSS transition is the right tool for a hover state.
4. **Concrete in-scope surfaces** (every Recharts chart component confirmed by direct inspection of `src/features/`): Dashboard's four charts (`spending-by-category-chart.tsx`, `income-vs-expense-chart.tsx`, `monthly-trends-chart.tsx`, `net-worth-history-chart.tsx`), Analytics' six charts (`category-trends-chart.tsx`, `yearly-spending-chart.tsx`, `income-sources-chart.tsx`, `expense-distribution-chart.tsx`, `savings-growth-chart.tsx`, `income-growth-chart.tsx`), Investments' two charts (`growth-chart.tsx`, `allocation-chart.tsx`), Financial Goals' `net-worth-trend-sparkline.tsx`, and Financial Health Score's `financial-health-score-history-chart.tsx`.
5. **Analytics' spending heatmap** (`spending-heatmap.tsx`) is a custom-built visualization, not a Recharts component (confirmed directly — no `recharts` import in that file) — it is still in scope for this capability's spirit (a data visualization on a data-visualization-heavy screen) and gets the identical bounded, CLS-free entrance treatment, but via Framer Motion (since it has no Recharts-native animation prop to lean on), not via item 3's mechanism.
6. **Concrete out-of-scope surfaces:** Reports (`/reports`) and every Admin route render no Recharts (or any other chart) component today (confirmed by direct inspection) — nothing in this capability applies to either.
7. **Reduced motion:** every chart's data renders fully-drawn on first paint, with no growing/drawing/sweeping entrance and no animated transition between old and new data on update.

### Edge Cases

- **A chart with no data** (a new category with zero transactions, an investment with no history yet): no entrance animation is attempted — the chart's own existing empty-state message renders instantly, since there is nothing to animate and no CLS risk on this path.
- **A chart re-rendering due to a window-resize or breakpoint change, not a data change:** the entrance animation never replays — resize/orientation-change is a layout event, not a data event, and must never retrigger a "growing bars" animation.
- **Rapid, successive data updates** (a user quickly clicking through several months on a period selector before a previous chart's update animation finishes): the newest update's animation takes over cleanly — no stacked, competing, or flickering tweens from an interrupted prior animation.
- **A chart rendered inside 5a's horizontal-scroll-with-affordance container** (`ScrollAffordanceContainer`, Analytics' resolved mobile treatment): this capability's CLS bar applies to the chart's own box only — the scroll container's static CSS edge-gradient affordance is unrelated and unaffected by this capability's animation work.

## Capability: Page Transitions

### Acceptance Criteria

1. **Every in-app navigation between authenticated `(dashboard)` route-group routes** (via `Sidebar`, `BottomNav`, `TopNav`, or an in-app link) **gets a consistent, bounded-duration entrance transition for the newly-navigated-to route's content** — one shared wrapper, not a per-route implementation.
2. **No Time-to-Interactive regression:** the new route's interactive elements are operable (clickable, focusable, typeable) no later than the moment the transition's own visual animation completes, and ideally before — the CTO's binding wording, restated as a directly measurable bar for the Performance Engineer's later review.
3. **Does not interfere with, race, or double up on Next.js's existing streaming `loading.tsx` skeletons** — the transition wrapper composes around whatever Suspense/`loading.tsx` behavior a given route already has, rather than layering a second, separate fade/skeleton on top of it (a route's own streaming skeleton fading in while a separate page-transition wrapper also fades the shell in would read as janky/redundant, not smooth — directly the opposite of this phase's own goal).
4. **Scope: the authenticated `(dashboard)` route-group only.** Explicitly **not** in scope:
   - **The `/login` → authenticated-app transition** — a full auth redirect with its own server-driven session-establishment latency; a decorative page-transition wrapper should not attempt to mask or take credit for that materially different kind of navigation event.
   - **Admin's own separate layout tree** (`/admin/*`) — Admin is internal team tooling, not a consumer-facing flow; consistent with 5a's own lighter-touch precedent for Admin, this capability's dedicated wrapper is not applied there. Admin's existing navigation must not regress (no added jank), it simply does not receive the new decorative treatment.
5. **Reduced motion:** the route swap is instant — new content simply appears, no fade/slide of any kind. Page transitions are named here explicitly as the highest-priority instance for this phase's reduced-motion automated test coverage, since a full-viewport motion effect on every navigation is the class of animation most likely to be experienced as genuinely uncomfortable by a user who has set this OS-level preference.

### Edge Cases

- **Navigating to a dynamic detail route whose own server-fetched data takes longer to resolve than the transition's own duration** (e.g. `/transactions/[id]`): the transition animates only the shell/skeleton-to-content handoff and never extends its own duration to "wait for" a slow fetch — a slow fetch remains `loading.tsx`'s job, unchanged by this phase, per AC3.
- **Rapid successive navigation** (a user double-clicking a nav item, or clicking a second destination before the first transition finishes): the newer navigation's transition takes over immediately and cleanly — no stacked or backed-up queue of pending transitions.
- **Browser back/forward navigation:** behaves consistently with forward in-app navigation — not skipped, not visually different in the reverse direction.
- **A "navigation" that resolves to the currently-active route** (e.g. clicking the already-active `Sidebar`/`BottomNav` item again): no transition plays at all, since no actual route change is occurring.

## Capability: Expandable Cards

Grounded by direct inspection: **no dedicated, reusable disclosure-widget primitive exists anywhere in this codebase today** (confirmed — no `Collapsible`/`Accordion` component exists under `components/ui/` or anywhere in `src/`). The one existing ad hoc instance of this interaction pattern, Analytics' "Dismissed merchants" toggle (`features/analytics/components/subscriptions-list.tsx`), sets `aria-expanded` correctly but has no `aria-controls` linking the trigger to the disclosed region — an incomplete instance, not a reference model to copy. This is genuinely starting close to zero as an audited, reusable practice, the same class of finding 5a's own kickoff pass made about accessibility tooling before that phase began.

### Acceptance Criteria

1. **One single, reusable expandable-card/disclosure-widget primitive is used everywhere this app needs a "reveal more detail inline, without navigating to a new page" interaction** — not reinvented per screen (CTO-set, UI Component Engineer ownership, restated).
2. **Correct, complete ARIA semantics on every consumer:** the trigger element carries `aria-expanded` (reflecting live state) and `aria-controls` referencing the disclosed region's real DOM id — closing the exact gap found in the one existing ad hoc instance above, for every consumer old and new, not `aria-expanded` alone.
3. **Expand/collapse is orchestrated via Framer Motion** (an animated height/opacity reveal), not a plain CSS transition — this is squarely the "orchestrated motion" category the CTO's Section 3 reserves Framer Motion for, distinct from the one-line hover-state color change CSS/Tailwind utilities remain the default tool for.
4. **Concrete named consumers this phase applies the primitive to:**
   - **Analytics' existing "Dismissed merchants" disclosure** (`subscriptions-list.tsx`): migrated from its current ad hoc `useState` + ghost-button implementation onto the shared primitive, gaining the missing `aria-controls` and the new animation for free, with its existing dismiss/undo *behavior* left completely unchanged — only the toggle's own implementation changes.
   - **Every mobile card-list row rendered by 5a's `DataTableCardList`** across all five confirmed consumers (Transactions, Admin's `UserTable`/`AuditLogTable`, Bills'/Recurring Income's `OccurrenceHistoryTable`): each card gains a per-card expand affordance revealing that row's remaining detail not otherwise shown at a glance — directly satisfying this phase's own composition requirement that the primitive work correctly inside a `DataTableCardList` card, not just a bare hypothetical one. The exact split of which fields sit behind the toggle versus remain always-visible per card is a Frontend Lead/UI Component Engineer implementation call (mirroring 5a's own "primary/secondary annotation is the Frontend Lead's call" precedent) — this AC's product-level requirement is only that a working, accessible, animated expand affordance exists and is reachable on every card-list row across all five consumers.
   - **Any other ad hoc "click to reveal more" instance the implementation pass's own systematic sweep of the full route inventory finds** beyond the one confirmed above — this spec does not claim exhaustive prior knowledge of every such instance by inspection alone; finding and migrating any other one found is part of this capability's own "systematic pass, not per-feature bolt-on" bar, the same standard every other 5b capability is held to.
5. **Reduced motion:** expand/collapse becomes an instant show/hide — content still toggles correctly and instantly, and `aria-expanded` still updates correctly and immediately, with no height/opacity tween.
6. **Never a replacement for an existing dedicated detail-page navigation.** Goal/Bill/Debt/Income "card" components that already link to their own `/goals/[goalId]`-style detail route keep that link exactly as-is — this primitive is for revealing already-rendered detail inline on a card with no detail page of its own (the `DataTableCardList` row case) or a genuinely optional secondary list (the dismissed-merchants case), never a substitute for an existing, dedicated detail-page pattern.

### Edge Cases

- **A card's underlying data changes while it is expanded** (e.g. a mobile Transactions card is marked as split while its expand affordance is open): the expanded state persists across the update — it does not silently collapse — and the revealed content reflects the new data.
- **Multiple cards in the same list expanded simultaneously:** no artificial single-expanded-at-a-time constraint is required; each card's expand state is independent.
- **A card's expand toggle sharing space with the row's own existing per-row action control** (Transactions'/Admin's `MoreHorizontal` menu, Bills'/Recurring Income's Mark Paid/Unmark button): the two controls remain independently operable and spatially distinct, so that expanding a card never accidentally triggers the row's own action button and vice versa — a real touch-target-adjacency risk on the smallest supported viewport, tied directly to 5a's own 44×44px minimum touch-target bar.

## Cross-Cutting: GPU-Compositable-Properties Bar

This is a concrete, checkable bar for the Performance Engineer's later 5b review gate (roadmap Section 1), not a sixth motion surface — it applies across every capability above.

### Acceptance Criteria

1. **Every animation this phase adds or touches prefers `transform`/`opacity` over `width`/`height`/`top`/`left` wherever the intended visual effect can be achieved that way** (CTO-set, restated).
2. **Two named, reasoned exceptions — decided here rather than left ambiguous for the Performance Engineer to discover only at review time:**
   - **Expandable cards' height reveal** (Capability above): a disclosed region's height genuinely changes as content enters/leaves layout flow, and correctly reflowing surrounding content requires animating `height` (or an equivalent measured-height technique) — there is no `transform`/`opacity`-only way to achieve a real content reveal that pushes surrounding elements. Accepted as this phase's one deliberate exception.
   - **`ProgressRing`'s existing SVG `strokeDashoffset` animation** (pre-existing, shipped before this phase, unrelated to any new 5b work): a paint-tier property, not a layout-triggering one like `width`/`height` — it does not force reflow, though it is not literally `transform`/`opacity` either. Treated as an accepted pre-existing exception, not newly introduced by this phase, and left to the Performance Engineer's own review to confirm it remains cheap rather than rebuilt speculatively here.
3. **Every other motion surface in this phase** (number-counter text content, chart entrance/update opacity and native Recharts animation, page-transition container opacity/transform, expandable-card content fade-in) **has no exception and must comply without one.**

## Open Questions Resolved by This Spec

The kickoff pass's Section 5 open questions (reduced-motion persistence, bottom-nav relationship, visual-regression tooling) were all resolved before this spec was written — the first two by 5a's own Product Owner spec, the third by 5a's Solution Architect pass, with an explicit revisit trigger tied to this phase (`phase-5a-technical-design.md` §6: "if 5b's later motion pass... surface a real, shipped visual regression... 5b's (or a later) Solution Architect pass should weigh it fresh at that point"). None of those three is re-litigated here; the visual-regression trigger is the Solution Architect's own call to make if this phase's implementation surfaces the evidence it names, not a question this Product Owner spec answers preemptively.

The kickoff pass's Section 3 constraints for 5b, however, left several concrete numbers and scope boundaries unfixed — the same kind of gap 5a's own spec had to close for the responsive workstream's per-surface mobile-treatment decisions. Resolved here, explicitly:

1. **Chart-transition duration bound: 400–800ms**, distinct from and slightly longer than number counters' CTO-fixed 300–600ms. Reasoning: the CTO's own constraint gives counters an explicit number but only says "bounded, consistent" for charts — leaving the actual figure to this spec. A chart's entrance (multiple bars/points/segments animating in together) is a visually denser event than a single number ticking, and Recharts' own commonly-used default animation durations (typically in the 800–1500ms range for entrance animations) run longer than what this phase's "restrained, not showy" craft goal wants; splitting the difference at a range shorter than Recharts' own defaults but longer than a single counter's tick reflects that a chart is a more visually complex event than one number, without drifting into the kind of slow, showy animation this project's Business Value section explicitly does not want ("smooth," not "slow").
2. **Expandable cards' concrete application scope beyond the one existing ad hoc instance**: resolved as (a) migrating that one existing instance (Analytics' dismissed-merchants toggle) onto the new shared primitive, and (b) applying the primitive to every one of 5a's five `DataTableCardList` consumers' mobile card rows, per this phase's own explicit instruction that the primitive must compose correctly inside a `DataTableCardList` card, not just a hypothetical bare one. Reasoning: the kickoff pass names "expandable cards" as one of five motion surfaces without enumerating consumers (unlike the responsive workstream's data-heavy-surface list in 5a, which the CTO's kickoff pass named explicitly) — this spec supplies that enumeration directly from what's confirmed to exist today (one ad hoc instance) plus what the "must compose inside `DataTableCardList`" instruction structurally requires (the five card-list consumers), rather than leaving "expandable cards" as an undefined aspiration with no concrete surface to build against.
3. **Number counters' inclusion/exclusion scope**: the out-of-scope side (Transactions' row-level amounts, Reports' static PDF output, Admin's absence of financial figures) is resolved as originally written, reasoning stated inline in that capability's own AC7, not repeated here.

   The in-scope side required a targeted revision after the CTO's 2026-08-03 resolution pass found a genuine internal contradiction: AC1, as originally drafted, defined this capability's applicability strictly by rendering component (`StatCard`/`ProgressRing`), while AC6 named ten surfaces as in-scope — six of which (Accounts, Debt, Investments, Analytics, and both Financial Health Score surfaces) render their headline currency/percentage figures via plain `formatCurrency`-driven `<span>` elements today, never through `StatCard`/`ProgressRing`. Read literally, AC1 would have silently excluded those six surfaces despite AC6 explicitly promising them; an implementer trying to honor AC6 instead would have had to invent a second, per-consumer counting mechanism, directly violating this same capability's own "one consistent treatment, not tuned per consumer" bar (AC2).

   **Resolution: AC1's mechanism definition is broadened to cover every headline currency/percentage figure that flows through the `formatCurrency`/`useFormatCurrency` pipeline (Phase 4c), application-wide, regardless of which component — `StatCard`, `ProgressRing`, or a plain `<span>` — happens to render it.** AC6's ten-surface list is unchanged and is now correctly grounded by that broadened definition rather than contradicted by it. Reasoning:
   - **The User Story's own framing already promised this.** It describes "the numbers... I interact with every day" broadly, not "the numbers that happen to render through one particular shared component" — a narrower reading that excluded Accounts, Debt, Investments, Analytics, and the Financial Health Score (five of this product's most prominent net-worth-and-progress surfaces, and arguably the single most "headline" number in the app — the Financial Health Score's own numeric score, which AC4 already separately commits to giving identical counting treatment to currency figures) would visibly contradict the phase's own stated value proposition, not just an implementation detail.
   - **Cutting six of ten already-promised surfaces (the narrower alternative considered) is a real, user-visible regression, not a neutral scope trim.** A Dashboard net worth figure that counts up while an Accounts balance two clicks away jumps instantly would read as an inconsistency a user would notice, directly undermining this phase's own "one consistent treatment" bar (AC2) at the product-experience level, not just the implementation level.
   - **This is a product-scope decision, not an implementation one, and is made on that basis.** Defining the capability's applicability by *what figure* is covered (any headline currency/percentage figure, sourced through the one already-established formatting pipeline) rather than *by which existing component happens to render it today* is a statement of product intent. Which component (or new primitive) actually renders each of the ten surfaces' figures, and whether any of the six affected surfaces are migrated onto `StatCard` as part of that primitive's design, is deliberately left to the Solution Architect and UI Component Engineer — consistent with this document's own opening statement that it does not design the counter primitive's integration boundary. This spec commits only to *what* must animate, not *how*.
   - **No new AC7 exclusion is created by this broadening.** AC7's existing exclusions (Transactions' row-level amounts, Reports, Admin) remain reasoned on "headline vs. row-level" and "no live DOM figure to animate" grounds that are independent of which component renders a figure — broadening AC1's mechanism does not pull any of AC7's excluded surfaces back into scope, since none of them fail AC7's exclusion for lack of a `StatCard`/`ProgressRing` wrapper in the first place.

   This closes the gap the CTO's 2026-08-03 resolution pass raised (Risk #53) without reopening its sibling finding (Risk #55, `StatCard`'s current already-formatted-string prop contract) — that remains, correctly, the Solution Architect's implementation-boundary question to resolve, not one this revision answers.
4. **Page transitions' route-tree scope**: resolved to the authenticated `(dashboard)` route group only, excluding the `/login` redirect and Admin's separate layout tree — reasoning stated inline in that capability's own AC4.
