# Product Spec — User Customization (Phase 4c)

This document covers User Customization, one of Phase 4c's three parallel domains (Calendar v2 and Admin are spec'd separately; all three are dispatchable in parallel per `roadmap.md`'s Phase 4c milestone 1). It is a **product** spec: it does not design the per-user preferences table, does not pick the admin-authorization mechanism (not this feature's concern at all), and does not lay out the settings page's UI — those are the Solution Architect's and Frontend Lead's calls. Three scope boundaries from the Roadmap's Phase 4c CTO kickoff pass (2026-07-29) are binding on everything below, restated here so an implementing agent never has to reconstruct them from `roadmap.md`:

1. **Dashboard layout/widgets** is show/hide + reorder of the existing fixed set of Dashboard cards only — explicitly **not** a drag-and-drop widget-builder framework, a pluggable third-party-widget system, or a per-widget-configurable-parameters system.
2. **Currency display** is a display-formatting preference only (which currency symbol/locale number-grouping convention renders already-USD-denominated amounts) — explicitly **not** multi-currency data support. No `Account`, `Transaction`, or any other model has a currency field, and none should be added; nothing is converted, only re-formatted.
3. **Timezone preference** is a genuinely new per-user field — no prior implementation exists in this schema despite Risk #8's stale claim to the contrary (confirmed by the CTO kickoff pass's direct schema grep). It exists so date-boundary logic across the app can be computed against the user's actual local time instead of server/UTC time.
4. **Custom categories are explicitly out of scope** — Categories CRUD already shipped in Phase 1 (`docs/product/categories.md`) and is not this feature.

## User Story
As a FinanceOS user, I want to make the dashboard look and feel like mine — my preferred color theme, only the cards I care about in the order I want them, amounts formatted the way I'm used to reading them, and dates that reflect my own timezone rather than some server somewhere — so the app feels personal and its dates/numbers are trustworthy rather than subtly foreign or misleading.

## Business Value
Every prior phase added financial substance (data, insight, delivery channels); this phase adds no new financial capability at all, and that is deliberate — it is the point in the roadmap where the product stops being "a tool that works" and starts being "a tool that feels like mine," a distinction Phase 5 (Motion & Craft) will later build on further. Concretely:
- **Themes/accent colors and dashboard layout** are retention and satisfaction levers: a returning user who has arranged the dashboard around what they personally check first (e.g. Budget Health Score before Net Worth) engages faster and more consistently than one facing a fixed, one-size-fits-all layout.
- **Currency display** removes a small but real friction point for any user who reads `$1,234.56`-style grouping less naturally than a different convention — a low-cost, high-goodwill fix given the underlying data model needs no change to support it.
- **Timezone preference** is not cosmetic — it closes a genuine correctness gap. Every date-boundary decision this product has made since Phase 2 (is this bill due today or late, has this month's budget reset, has this month closed for summary generation) has been silently computed against server time. For any user not physically near that server's timezone, "today" and "this month" may already be wrong by up to a full day at the boundary — a trust-eroding defect in a product whose entire value proposition is being a source of truth about a user's money and obligations.

## Where These Preferences Live
Every capability below needs a durable, per-user home reachable from the app (a dedicated settings surface, presumably a single page, per the existing pattern established by 4b's notification-preferences screen) — but this spec does not dictate that page's layout, grouping, or navigation entry point; that is the Solution Architect's and Frontend Lead's call. What is required, as a product-level capability, is that each of the four preferences below:
- Is individually viewable and editable by the authenticated user, scoped strictly to their own account (no exception to the standing per-user data-isolation discipline, Risk #4).
- Persists across sessions and devices (a preference set on desktop is honored on mobile, and vice versa) — this rules out a client-only/local-storage-only implementation as sufficient on its own.
- Takes effect app-wide immediately upon save, without requiring the user to know to visit any other page to "see it apply." A preference is not considered saved until every dashboard, report, and notification surface reflects it going forward.

## Capability: Theme & Accent Color

The existing light/dark/system mode toggle (`src/components/shared/theme-toggle.tsx`, `theme-provider.tsx`) already ships and is unaffected by this feature — this capability adds a **second, independent** preference (accent color) on top of it, not a replacement.

### Acceptance Criteria
1. A user can choose an accent color from a fixed set of preset options (not a freeform color picker) — the specific palette is a Frontend Lead/UI Component Engineer design decision, but the product requirement is a small, curated set (on the order of five to eight options) sufficient to feel personal without becoming a color-theory support burden.
2. The accent color preference is independent of, and composable with, the existing light/dark/system mode toggle — a user can pair any accent color with any mode.
3. The existing top-nav light/dark/system `ThemeToggle` quick-switcher is unchanged, remains where it is, and is not removed, replaced, or duplicated by this feature. Accent color selection lives only in the new settings surface (per "Where These Preferences Live," above) since it is a set-once-and-forget preference, not one that benefits from a header-level quick toggle the way light/dark does.
4. The chosen accent color applies consistently everywhere the product currently uses a primary/accent color token (buttons, active nav states, chart highlight colors, progress bars) — this is a token-level preference, not a per-screen one.

### Edge Cases
- **A user who never sets an accent color**: sees the product's current default accent color, unchanged from today — this feature must not force an explicit choice before a user can use the app.
- **A future new accent-color-using surface** (a new card, a new chart): inherits whatever the user's saved preference already is; nothing about this feature requires touching every future feature's code, only the shared color token(s) they already pull from.

## Capability: Dashboard Layout (Show/Hide + Reorder)

Applies to the existing fixed set of Dashboard cards as they exist after Phase 4a/4b — illustratively: Net Worth, Monthly Income, Monthly Expenses, Cash Flow, Savings Rate, Remaining Budget, Budget Health Score, Financial Health Score, Monthly Summary, Spending Insights, Net Worth History, and the three charts (Spending by Category, Income vs. Expense, Monthly Trends). The authoritative, exact card set is whatever the Frontend Lead's current Dashboard implementation actually renders — this spec governs the *interaction model* over that set, not the enumeration itself, since the set is expected to grow slightly over time as new phases ship.

### Acceptance Criteria
1. A user can hide any individual card from their Dashboard and unhide it later; a hidden card's underlying data/computation is entirely unaffected (hiding is a display preference, never a deletion or disabling of the feature itself — e.g. hiding the Budget Health Score card does not stop the score from being computed, nor remove it from its own detail view).
2. A user can reorder their visible cards into any sequence they choose.
3. **At least one card must remain visible at all times.** A user attempting to hide the last remaining visible card is blocked, with a clear explanation, rather than being allowed to produce a completely empty Dashboard — an empty Dashboard would read as broken or in an error state, the same "never a blank space... or an error" bar `dashboard-overview.md`'s own empty-state Edge Cases already hold every other Dashboard state to.
4. An explicit **"Reset to Default Layout"** action is available, restoring every card to visible and to the product's own canonical default order in one step, without requiring the user to manually toggle/reorder each card back individually.
5. Charts (Spending by Category, Income vs. Expense, Monthly Trends) and stat cards are both members of the same show/hide/reorder set — this feature draws no distinction between "chart" and "card" for customization purposes; a user may hide a chart exactly as they would hide a stat card.

### Edge Cases
- **A new Dashboard card ships in a later phase** (e.g. a future 5-and-beyond addition): defaults to **visible**, and is appended to the **end** of a user's existing custom order — it never silently disappears into a hidden state the user never chose, and it never inserts itself into the middle of an order the user deliberately arranged.
- **A card a user previously hid becomes temporarily inapplicable for a different reason** (e.g. Remaining Budget's own "no budget set" empty state from `budgeting.md`): the user's hide/show preference is unrelated to, and takes precedence over, that card's own internal empty-state logic — if the user chose to show it, it renders its own existing empty state exactly as it does today; if the user chose to hide it, it does not render at all, regardless of whether it would have had an empty state or real data to show.
- **A user who never touches this feature at all**: sees every card, in the product's existing default order, unchanged from today — this feature is additive and never degrades the out-of-the-box experience.

## Capability: Currency Display

A pure display-formatting preference — which currency symbol and number-grouping convention is used to render amounts that are, and remain, plain USD-denominated numbers under the hood. Extends `formatCurrency` (`src/lib/utils.ts`), currently hardcoded to `en-US`/`USD`.

### Acceptance Criteria
1. A user can choose a display currency from an initial, curated list: **USD (default), EUR, GBP, CAD, AUD, JPY.** This set is chosen to cover the symbol/grouping conventions most likely relevant to this product's actual user base (a personal-finance dashboard, English-language, primarily Western-market audience) plus one zero-decimal currency (JPY) to ensure the preference genuinely handles a structurally different formatting convention (no decimal places), not merely a symbol swap on an otherwise-identical number. This is a deliberately small starting list, not an attempt to cover every ISO currency; expanding it later is a low-risk, additive change if real demand surfaces.
2. Choosing a non-USD display currency **never changes any stored, computed, or compared numeric value** anywhere in the product — every calculation (Net Worth, budget math, debt payoff schedules, Analytics aggregates, threshold comparisons for Large Purchase/Low Balance notifications) continues to operate on the same underlying USD figures exactly as it does today. Only the rendered symbol and number-grouping convention change.
3. Because this could otherwise mislead a user into thinking their money has been converted, the settings UI must present this control under a label and helper text that makes the "formatting only, not conversion" distinction explicit (e.g. "Currency Display Format" rather than bare "Currency," with copy to the effect of "changes how amounts are shown — your data stays in USD"). This is a product requirement, not a UI nicety, given the real risk of a user misreading a re-symbolized number as a converted one.
4. The preference applies to **every currency-formatted figure in the product**, with no exceptions carved out: Dashboard cards, Transactions, Accounts, Budgeting, Bills, Debt Tracker, Investments, Savings Goals, Financial Goals, Analytics, all six Reports PDF types (including their tabular/numeric content), and notification/email content (Large Purchase, Low Balance, and any other currency-figure-bearing notification or email). A user who sets a display currency and still sees a stray `$`-formatted figure anywhere is a defect.
5. Changing this preference takes effect for all **future** rendering only — it does not retroactively alter any already-downloaded PDF report or already-delivered notification/email (those are static artifacts at the moment they were generated/sent); the next report generated or notification sent after the change reflects the new preference.

### Edge Cases
- **A user who never sets a display currency**: sees USD formatted exactly as today (`$1,234.56`, `en-US` grouping) — no behavior change for the default case.
- **A very large or very small figure in a non-USD display currency** (e.g. a six-figure net worth rendered with JPY's zero-decimal convention): must still format legibly and never round or truncate in a way that changes the displayed value's meaning beyond the chosen currency's own standard decimal convention.
- **A negative figure** (e.g. negative net worth, a liability): the chosen currency's formatting convention must still clearly convey negativity, consistent with every existing spec's "never hide a negative figure" precedent (`dashboard-overview.md` Edge Cases, `net-worth-history.md` Edge Cases).

## Capability: Timezone Preference

A genuinely new per-user field (Risk #8, extended). Selected from a dropdown of IANA timezone names (e.g. `America/New_York`, `Europe/London`, `Asia/Tokyo`) — the standard, unambiguous way to represent a user's local time including that region's own daylight-saving rules, rather than a raw UTC-offset number that would silently break twice a year in regions observing daylight saving time.

### Acceptance Criteria
1. A user can select their timezone from a searchable list of standard IANA timezone names.
2. Every existing feature whose logic currently depends on "what day is it" or "has this month boundary passed" must evaluate that decision against the user's stored timezone, not server/UTC time, going forward. The complete, explicit list of affected existing features:
   - **Bills** (`bills.md`): each occurrence's Upcoming / Due Today / Late status computation, and the due-date-proximity window Notifications v1's "bill due soon" trigger uses.
   - **Budgeting** (`budgeting.md`): which calendar month is "the current month" for the planner, the monthly reset boundary, and the over-budget notification's "once per category per month" boundary.
   - **Calendar v2** (this phase's sibling spec, `docs/product/calendar-v2.md`): correct day-cell placement for bill occurrences, payday occurrences, and the budget-reset marker — a zero-schema view composing the three sources above, so it inherits this fix automatically once they're corrected, but is called out explicitly since it is the most visually direct place a timezone-boundary bug would be noticed by a user.
   - **Recurring Income** (`recurring-income.md`): payday occurrence dates, on the same basis as Bills' occurrence dates.
   - **Dashboard month-to-date figures** (`dashboard-overview.md`): Monthly Income, Monthly Expenses, Cash Flow, and Savings Rate's "current calendar month to date" window.
   - **Analytics** (`analytics.md`): the shared reporting-period control's "This Year / Last 12 Months / Year-to-Date" boundaries.
   - **Automatic Monthly Summaries** (`ai-features.md` Feature 3): the "has this month fully closed yet" gate that determines when a month's summary is generated.
   - **Notifications v2's Monthly Summary trigger** (`notifications-v2.md`): fires "once per user, once per calendar month" — that month boundary must match the user's own timezone.
   - **Financial Goals' Savings Rate Target type** (`financial-goals.md`): the rolling 3-month-average window's month boundaries.
   - **Reports** (`reports.md`): the Monthly and Yearly report types' period boundaries, and any custom date-range report's interpretation of "which day" a start/end date refers to.
   - **Net Worth History's "as of" labeling** (`net-worth-history.md`): which calendar day a snapshot's label reflects.
3. The underlying stored data (transaction dates, bill due dates, snapshot timestamps, etc.) is not reinterpreted or migrated by this feature — this preference changes how "today"/"this month" boundaries are *computed going forward*, not how already-stored dates are represented at rest. (This is squarely an implementation detail for the Solution Architect's schema/service design, restated here only to make clear the product requirement is forward-looking boundary evaluation, not a data migration.)
4. The mechanism by which server-side scheduled jobs (the Monthly Summary cron, the Net Worth Snapshot cron, the Financial Health Score snapshot cron, and 4b's `evaluate-notifications` cron) determine "has this user's month/day boundary passed yet" must be evaluated per-user against that user's own timezone — regardless of what wall-clock time the underlying job itself happens to run at. (Again, the *how* — e.g. a single daily batch run that checks each user's local boundary vs. a per-user-scheduled trigger — is the Solution Architect's call; the product requirement is only that the boundary decision itself is timezone-correct.)

### Edge Cases
- **A user who never sets a timezone preference**: defaults to a sensible fallback rather than an unset/error state. **Decision: infer the user's timezone from their browser at signup (a one-time, best-effort capture, editable afterward exactly like any other preference) and fall back to UTC only if that inference is unavailable.** This is preferable to defaulting every new user to UTC outright, since a browser-inferred timezone is very likely correct on day one and avoids a known-wrong default silently shipping bugs into a brand-new user's very first bill/budget view; UTC remains the safety-net default of last resort, not the primary one.
- **A user changes their timezone after bills/budgets/reports have already been computed under the old one.** **Decision: this is forward-looking only — nothing is recomputed retroactively.** A bill occurrence already marked Late, a month's budget that has already reset, a `MonthlySummary` already generated, or a notification that already fired under the old timezone's boundary is left exactly as it was; only future boundary evaluations (the next "is this due today," the next month's reset, the next summary generation) use the new timezone. This is consistent with this product's own established precedent that history is never silently rewritten (`dashboard-overview.md` AC11 — archiving an account never rewrites history; `bills.md`'s schedule-change edge case — editing a bill's schedule affects future occurrences only) and avoids a confusing, potentially data-losing mass-recompute (e.g. a bill that was Late becoming retroactively Upcoming) triggered by what is, from the user's point of view, a simple settings change.
- **A user near the international date line, or in a timezone with an unusual UTC offset** (e.g. `Pacific/Kiritimati`, UTC+14): must be selectable and function identically to any other timezone in the list — no special-casing or exclusion of extreme-offset zones.
- **Daylight saving time transitions**: handled correctly by virtue of using IANA timezone names (which encode a region's own DST rules) rather than a fixed numeric UTC offset — this is precisely why a raw offset picker is rejected in favor of the IANA-name dropdown (AC1).

## Definition of Done
- A user can independently set, change, and clear/reset each of the four preferences above (accent color, dashboard card visibility/order, currency display, timezone), and each persists across sessions and devices.
- Accent color composes correctly with every combination of the existing light/dark/system mode, verified visually; the existing `ThemeToggle` component is confirmed unmodified and undisturbed by this feature.
- Dashboard card show/hide/reorder is verified against: hiding all-but-one card (allowed), attempting to hide the last visible card (blocked, with explanation), the "Reset to Default Layout" action (fully restores visibility and canonical order), and a simulated "new card ships later" scenario (new card defaults to visible, appended to the end of an existing custom order).
- Currency display is verified, by test, to change rendered symbol/grouping only — the exact same underlying numeric values, calculations, and threshold comparisons (budget math, debt payoff, Large Purchase/Low Balance notification thresholds) are confirmed unaffected by a currency-display change, across every surface listed in AC4 above (Dashboard, Transactions, Accounts, Budgeting, Bills, Debt, Investments, Savings/Financial Goals, Analytics, all six Report types, notifications/email).
- Timezone preference is verified, by test against fixture users in several distinct timezones (including at least one ahead of UTC and one behind, and one non-integer-offset zone), to produce correct Upcoming/Due Today/Late bill status, correct budget month-reset timing, correct Dashboard month-to-date figures, and correct Monthly Summary/Notifications v2 monthly-trigger timing — matching what a user physically in that timezone would expect "today" and "this month" to mean.
- Verified, by test, that changing a user's timezone preference does not alter any already-computed historical state (already-Late bills, already-closed budget months, already-generated `MonthlySummary` rows, already-fired notifications) — only future boundary evaluations are affected.
- Verified that a user who never touches any of these four preferences experiences the product completely unchanged from its current (pre-4c) behavior in every respect — default accent color, full default card set/order, USD/`en-US` formatting, and browser-inferred (or UTC fallback) timezone.
- Meets the release-level bar defined in the Project Charter: tests passing, Security Architect review (preferences strictly scoped to the authenticated user's own account, per Risk #4 — no exception introduced by a new preferences table), Performance Engineer review (no material regression to Dashboard load time from adding per-user layout/formatting resolution), documentation, and CTO/architecture sign-off.

## Dependencies
- Dashboard Overview (Phase 1) and every phase that has added a Dashboard card since (Budgeting's Budget Health Score, 4a's Financial Health Score/Monthly Summary/Spending Insights, 3b's Net Worth History): the show/hide/reorder capability operates over this existing, evolving card set.
- The existing light/dark/system `ThemeToggle`/`ThemeProvider` (`src/components/shared/theme-toggle.tsx`, `theme-provider.tsx`, Phase 0): accent color is additive to this, not a replacement.
- `formatCurrency`/`formatDate` (`src/lib/utils.ts`, Phase 0/1): the currency-display and timezone preferences extend these existing utilities' behavior; every feature that already calls them inherits the new preference automatically once the utilities themselves are updated, rather than needing per-feature changes.
- Bills, Budgeting, Recurring Income, Calendar v2 (this phase's sibling spec), Dashboard, Analytics, Automatic Monthly Summaries, Notifications v2, Financial Goals, Reports: all listed explicitly in the Timezone Preference capability's AC2 as consumers whose date-boundary logic must be updated.
- Calendar v2 (Phase 4c, dispatched in parallel): timezone-correct day-cell placement is inherited from the Bills/Recurring Income/Budgeting fixes above, not a separate implementation this spec requires of Calendar v2 directly.
- A new per-user preferences data model (Solution Architect + Database Architect's 4c combined pass, per `roadmap.md`'s Phase 4c milestone 3): not designed in this document.

## Success Metrics
- Percentage of active users who set at least one of the four preferences within their first month of this feature shipping (adoption signal for whether "make it feel like mine" resonates).
- Percentage of users who customize Dashboard card visibility/order specifically, and the most commonly hidden/reordered cards (informs which cards are genuinely load-bearing for users vs. which are routinely hidden — a signal worth revisiting in a future Dashboard iteration).
- Reduction in any prior support/feedback signal about incorrect "today"/"late"/"this month" behavior for users outside the server's own timezone, following the timezone preference's release (the concrete correctness problem this capability exists to fix).
- Zero reported incidents of a currency-display change altering any computed or compared numeric value.
- Zero reported incidents of one user's preferences (theme, layout, currency, timezone) leaking into or affecting another user's view.
