# Product Spec — Calendar v2 (Phase 4c)

## User Story
As a FinanceOS user, I want my calendar to show not just my bills but also when my paychecks (and other income) are expected, and to see where each month's budget cycle starts, so I get one complete, at-a-glance picture of my month — what I owe, what's coming in, and when my spending plan resets — instead of having to mentally combine three separate screens myself.

## Business Value
Calendar v1 (Phase 2) proved the value of a calendar as a low-cost, high-clarity way to answer "what's happening this month" for Bills alone. Since then, Recurring Income (Phase 3a) gave the app a second forward-looking, schedule-based data source — paydays — that was explicitly deferred from Calendar v1 for exactly this reason: it didn't exist yet (`calendar-and-notifications.md`'s own "Scope note: paydays are deferred"). Recurring Income has since shipped, so this deferred promise is now due. Layering paydays and a budget-cycle annotation onto the same calendar turns it from "a second view of Bills" into the single place a user checks to understand their whole month — obligations, income, and planning cycle together — without three separate mental models. Because it introduces no new data of its own (per the CTO kickoff pass, `roadmap.md`'s Phase 4c section, point 1), it delivers this materially richer picture at very low implementation risk, extending a pattern that's already shipped and proven twice (Bills' occurrences, Recurring Income's occurrences) rather than inventing a new one.

## Scope Note: zero new data, three composed sources (binding, per CTO kickoff pass)
Per the Phase 4c CTO kickoff pass (`roadmap.md`, 2026-07-29), Calendar v2 is confirmed as a read-only view composing exactly three already-existing, already-reviewed data sources, and introduces **no new Prisma models and no new stored event of any kind**:
1. **Bills' recurring occurrences** — Calendar v1's existing scope, unchanged (`bills.md`).
2. **Recurring Income's occurrences ("paydays")** — newly added this phase (`recurring-income.md`), closing the gap Calendar v1 explicitly deferred.
3. **A "budget reset" marker** — a visual annotation of Budgeting's existing monthly-cycle boundary (`budgeting.md`), not a new stored event; nothing about Budgeting itself changes.

The roadmap bullet's mention of "recurring transactions" is **not** a fourth, new, generic recurring-transaction domain — the CTO kickoff pass traced and closed this ambiguity: it is this spec's own umbrella term for the same Bills occurrence data in point 1, carried forward unchanged. No `recurring-transactions.md` exists or is needed.

## Acceptance Criteria

### Bill occurrences (unchanged from Calendar v1)
1. A user can view a monthly calendar showing every bill occurrence due that month, placed on its due date, exactly as Calendar v1 already does.
2. Each bill entry shows at minimum the bill name and amount, and reflects the same status (Upcoming/Due Today/Late/Paid) defined in the Bills spec, visually treated exactly as Calendar v1 already established — adding paydays and the reset marker must not change or reinterpret any existing bill-status visual meaning.
3. Selecting a bill entry takes the user to that bill's detail, exactly as Calendar v1 AC4 already does.

### Paydays
4. Every active income stream's occurrence for the month is placed on the calendar on its expected (or actual, once received) date, showing at minimum the stream's name and amount, and its status (Upcoming/Expected Today/Not Yet Received/Received) as defined in `recurring-income.md` AC7.
5. **A payday must be visually distinguishable from a bill at a glance, without requiring the user to read any text.** This codebase has an established semantic-color precedent for financial data — red/green treatment already used for gains/losses, over-budget indicators, and negative-amortization warnings (`naming-standards.md`'s CSS/Tailwind section). A payday represents money coming in and is treated as the "positive" side of that same convention; a bill represents an obligation/money going out and keeps its existing Calendar v1 status-based treatment unchanged. Color is never the sole distinguishing signal (a colorblind user must still be able to tell them apart): each entry type additionally carries a distinct icon and label (e.g., an income/deposit-style icon and label vs. a bill/invoice-style icon and label). The exact color token, icon choice, and pixel-level treatment are the Frontend Lead's and UI Component Engineer's call, not specified here — this spec fixes the *requirement* (distinguishable by color convention + icon + label, consistent with the app's existing semantic-color pattern), not the visual design itself.
6. Selecting a payday entry takes the user to that income stream's detail (its occurrence/receipt history), the same interaction pattern Calendar v1 AC4 already established for bills — every entry type on this calendar behaves consistently: click an entry, land on its source.
7. **Irregular/One-off income streams** (`recurring-income.md` AC1/AC11, no generated schedule) appear on the calendar only for events the user has actually logged, on the date logged — never as a projected/guessed future occurrence, since by definition there is no cadence to project from. This is a deliberate difference from every other entry type on this calendar (bills and scheduled income streams are schedule-driven and always show a projected next occurrence even before the user acts).

### Budget reset marker
8. A single, non-amount-bearing marker appears on the 1st calendar day of every month shown (past, current, and future), representing the start of that month's Budgeting cycle — the same monthly boundary `budgeting.md` AC3/AC4 already defines (one budget per calendar month; a new month's planner starts from the previous month's carried-forward allocations). Exactly one marker per month view; Budgeting has no sub-monthly cycle to annotate.
9. The marker is visually distinct in *kind*, not just color, from bill/payday entries — it carries no dollar amount and is not a transaction-like occurrence, so it must not be rendered using the same entry-card treatment as a bill or payday (which always show an amount). It reads as a structural boundary annotation on that day (e.g., a divider/banner-style treatment on the day-1 cell), not as a line item competing with that day's bills/paydays for the same visual slot.
10. The marker always renders, regardless of whether the user actually set any budget allocations that month — it annotates the fixed structural fact that a new cycle begins, independent of whether Budgeting was used (mirrors `budgeting.md`'s own "no budget was set this month" edge case, which is a fact revealed only after navigating in, not a reason to hide the marker itself).
11. Selecting the budget reset marker navigates the user to the Budgeting page for that month (read-only if a past month, editable if current/future — exactly matching `budgeting.md` AC3's own read-only/editable rule), consistent with the same "click an entry, land on its source" pattern established for bills and paydays above (AC3, AC6). This is a deliberate design choice extending Calendar v1's existing precedent uniformly to all three entry types, rather than leaving the reset marker as an inert decoration while everything else on the same screen is clickable.

### Filtering/toggling
12. **No show/hide or filter control is introduced for any of the three entry types in this version.** With only three kinds of calendar content (bills, paydays, the reset marker), all shown together by default the same way Calendar v1 already shows all bill occurrences without any filter, a toggle would add UI complexity disproportionate to the actual number of things being distinguished. If real usage later shows a meaningful number of users want to hide one entry type (e.g., a user with no income streams set up who finds the calendar cluttered — though the empty-state edge case below already handles that specific case), that is a candidate for a future, separately-scoped enhancement, not part of this spec.

### Findability
13. Because Calendar v2 is no longer a Bills-only view — it aggregates three domains — it must remain easy to find as its own complete destination (e.g., reachable from primary navigation), not effectively hidden as a sub-toggle a user would only discover while already inside Bills. The exact navigation/routing structure is the Solution Architect's and Frontend Lead's implementation call, not specified here; this AC only states the product requirement that discoverability keep pace with the feature's now-broader scope.

## Edge Cases

- **A month with no bills due and no active income streams at all**: the calendar is not blank — the budget reset marker still renders (AC10, it is not data-dependent) — but there is nothing else to show. If the user has genuinely never set up any bill or income stream anywhere in the app (not just this month), the calendar shows a combined empty-state prompt pointing toward both Bills and Recurring Income setup, in the same tone as each domain's own zero-state (`bills.md`'s "Zero bills" edge case, `recurring-income.md`'s "Zero income streams" edge case) — not an error, and not two contradictory empty states stacked on top of each other.
- **A user with multiple income streams on different schedules** (e.g., a biweekly salary and a monthly rental): each stream's occurrences are computed and placed independently on their own dates. A day with more than one payday, or a day with both a bill and a payday, shows all of them in that day's cell without one crowding out another — the same "multiple bills due the same day" handling Calendar v1 already established (`calendar-and-notifications.md`), extended to cover mixed entry types.
- **The current, in-progress month vs. past/future months**: bills are unchanged from Calendar v1 (past/current/future all already supported). For paydays: past months show actual historical occurrences with their real Received/Not Yet Received outcome; the current and future months show projected Upcoming/Expected Today occurrences based on each stream's schedule — mirroring exactly how Bills already treats past vs. upcoming occurrences. The budget reset marker renders identically regardless of which month is being viewed (AC8/AC10).
- **Timezone / date-boundary computation**: this calendar renders dates, so which calendar day a bill, payday, or reset marker falls on depends on a per-user date-boundary computation this spec does not own or reimplement — see the Open Question below. Calendar v2 must use whatever date-boundary logic Bills, Recurring Income, and Budgeting themselves compute their own statuses and boundaries against; it must never independently compute a second, possibly-inconsistent notion of "what day is it" for the same underlying data.

## Open Question — flagged for the CTO resolution pass, not decided here
**Does Calendar v2 depend on Customization's (this same phase's sibling spec) new per-user timezone-preference field, and if so, is that dependency actually satisfiable by the time Calendar v2 ships?**

Risk #8's extension note (`risk-register.md`, added at this phase's kickoff) surfaces a genuine, previously-undocumented gap: no timezone field exists anywhere in the current schema, and Bills/Budgeting's actual shipped behavior has apparently been computing date boundaries against server/UTC time all along, not a "stored user timezone preference" as Risk #8's original Phase 2 text claimed. Customization (4c) is tasked with **adding** that field as new schema work, in the same combined Solution Architect + Database Architect pass that also covers Calendar v2 (`roadmap.md`'s Phase 4c milestone 3) — so the column itself should exist by the time backend implementation begins.

That does not, by itself, mean Bills', Recurring Income's, and Budgeting's own existing status/month-boundary computations get updated to *consume* that new field — those are each other feature's owned logic, out of this spec's scope to change, and none of their specs currently mention doing so as part of this phase. If the field is added by Customization but the three source features Calendar v2 composes keep computing against server/UTC time regardless, Calendar v2 should continue doing the same (rendering dates consistently with whatever its three sources actually do), and Risk #8's timezone gap remains open for those features specifically — not something this read-only, zero-new-schema view can or should resolve unilaterally on their behalf. **This spec deliberately does not decide whether Bills/Recurring Income/Budgeting's underlying computations get updated this phase** — that is a genuine cross-spec sequencing question the CTO resolution pass should confirm explicitly (does the timezone field land as schema-only groundwork this phase, with consuming logic updated in a later phase, or does 4c's scope quietly also require touching three other features' already-shipped, already-reviewed date logic?) rather than have an implementing agent guess.

## Definition of Done
- All three sources render correctly and stay in sync with their own systems — no drift: bill occurrences match Bills' own status data exactly (Calendar v1's original bar, unchanged); payday occurrences match Recurring Income's own status data exactly; the budget reset marker appears on exactly one date per month view, every month, matching Budgeting's own month-boundary definition.
- The visual distinction between bill occurrences, paydays, and the budget reset marker is implemented per AC5/AC9 (semantic-color convention + icon + label, verified for accessibility — not color alone) and confirmed not to alter any existing Calendar v1 bill-status visual meaning.
- Past, current, and future month navigation works correctly for all three source types, including the Irregular/One-off income event display rule (AC7), verified against real, varied data (multiple income streams on different schedules, mixed bill/payday days, a month with neither).
- The combined empty state (no bills, no income streams) and the reset-marker-always-renders behavior (AC10) are both verified explicitly, not just the "some data exists" happy path.
- Meets the release-level bar defined in the Project Charter: tests passing, Security Architect review (this remains a read-only composition scoped strictly to the authenticated user's own bills, income streams, and budget data — verified across all three sources, not just the bills-only surface Calendar v1's review already covered), Performance Engineer review (three sources composed on one view instead of one), documentation, and CTO/architecture sign-off.

## Dependencies
- **Bills** (Phase 2): unchanged data source, per Calendar v1's existing dependency.
- **Recurring Income** (Phase 3a): new data source this phase — occurrence dates, amounts, and status (`recurring-income.md`).
- **Budgeting** (Phase 2): source of the monthly-cycle boundary the reset marker annotates; Budgeting itself has no new dependency created by this feature, since the marker is view-only.
- **Customization** (Phase 4c, sibling spec): the newly-surfaced per-user timezone-preference field it introduces is relevant to how this calendar's dates render — see the Open Question above for what remains unresolved about that relationship.
- Calendar v1 (Phase 2, `calendar-and-notifications.md`): this spec is a direct extension of that one; nothing in Calendar v1's existing behavior is removed.

## Success Metrics
- Calendar view usage rate, continuing Calendar v1's existing metric — now measuring adoption of the richer three-source view against the Bills-only baseline it replaces.
- Among users who have both Bills and at least one active income stream set up, the rate at which they use the combined calendar versus checking Bills' Upcoming list and Recurring Income's expected-upcoming-income view separately (does the combined view actually replace two separate check-ins with one).
- Qualitative/at-a-glance distinguishability: absence of user-reported confusion between a bill and a payday on the calendar (proxy: support/feedback mentions, or a lightweight in-app survey), confirming AC5's visual-distinction requirement is actually working in practice, not just implemented on paper.
- Reset-marker click-through rate (AC11) as a signal of whether the marker's interactivity is discovered and used, informing whether that design choice was worth making versus a purely informational alternative.
