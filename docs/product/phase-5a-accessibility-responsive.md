# Product Spec — Phase 5a: Accessibility & Responsive Foundation

This document covers Phase 5a only — Accessibility and Responsive, the two structural workstreams the CTO's Phase 5 kickoff pass (`docs/planning/roadmap.md`, "Phase 5 CTO kickoff pass," 2026-07-30) split ahead of Phase 5b (Motion & Craft). It is a **product** spec: it does not choose the Playwright/axe-core bootstrap approach, does not design the bottom-navigation component's code boundary or its relationship to `components/shared/sidebar.tsx`, does not pick contrast-token fixes, and does not decide visual-regression tooling — those are the Solution Architect's, Frontend Lead's, and UI Component Engineer's calls. Phase 5b (motion, number counters, chart transitions, page transitions, expandable-card animation) is explicitly **not** covered here; it is a separate, later spec pass gated behind this one's own review gate passing, per the CTO's binding sequencing decision.

Every acceptance-criteria bar cited below as "CTO-set" comes from the kickoff pass's Section 3 and is binding, not a Product Owner suggestion — restated here so an implementing agent never has to reconstruct it from `roadmap.md`.

## User Story

As a FinanceOS user — regardless of the device I'm on, whether I navigate by mouse, touch, keyboard, or screen reader, and regardless of which accent color and light/dark theme I've chosen — I want every screen in the app to be fully usable: readable, reachable, operable without a mouse, and laid out correctly at my screen size, so that the product is genuinely usable by everyone who might rely on it, not just a keyboard-and-mouse desktop user on a wide viewport.

## Business Value

Every phase through 4c added financial substance or personalization; this phase adds neither — it is the point in the roadmap where the product's existing surface area gets audited and hardened rather than extended, the same "structural work before decoration" role 5a plays ahead of 5b per the CTO's own sequencing reasoning. Concretely:
- **Accessibility is not optional polish for a personal-finance product.** A user managing their own money is exactly the kind of user this product cannot afford to silently exclude — a keyboard-only user who can't reach the "add transaction" button, or a screen-reader user who can't tell whether a budget category is over or under, is a user who cannot safely use the product at all, not one having a merely worse experience. WCAG 2.1 AA is the industry-standard commercial bar (CTO-set, Section 3) and is the correct floor for a product whose stated ambition is "software someone would pay for."
- **Responsive completeness closes a real, already-partially-answered gap.** The CTO's own kickoff-pass finding (Section 2) is that this app is not desktop-only today — `Sidebar`/`TopNav` already collapse/hamburger correctly, and 117 responsive-class usages exist across 76 files — but that foundation was never verified systematically, route by route, against every screen shipped since Phase 0. A user on a phone hitting one broken, clipped, or unreachable screen anywhere in the app (a dialog that overflows the viewport, a data table that requires horizontal scrolling with no visual cue that more columns exist) reads as "this app is broken," not "this one screen wasn't finished," even if every other screen works.
- **This phase is a precondition for Phase 5b, not merely adjacent to it.** Per the CTO's dependency-chain reasoning (Section 1), animating a disclosure widget, a data table, or a mobile nav structure before that structure is finalized here means redoing the animation work once 5a restructures the underlying DOM. Shipping 5a correctly and completely is what makes 5b's investment durable rather than wasted.
- **This phase closes this project's largest tooling gap.** No accessibility testing has ever been performed at any point in this project's history, and the E2E Test Engineer role — whose own charter already names "Accessibility" as a required Playwright target — has never once been dispatched (Risk #41). This phase is also where that debt gets paid down, not merely where new screens get audited by hand.

## Capability: Accessibility

### Acceptance Criteria

1. **WCAG 2.1 AA is the binding target level, app-wide, for every route in the inventory above** — not a per-route judgment call, per the CTO's Section 3 constraint.
2. **Automated coverage**: an axe-core-based check runs against every route in the inventory, with zero critical/serious violations required to pass this phase's release gate. Any accepted moderate/minor finding is recorded as a named, owned backlog item (not silently dropped, not silently blocking indefinitely) — the same "flagged and tracked, not swept under the rug" discipline every prior phase's Definition of Done has held audit-style findings to.
3. **Full keyboard-only operability on every interactive surface** — data tables (Transactions, Admin's View Users, Audit Logs), dialogs (`Dialog`), sheets (`Sheet`, including the mobile nav trigger), dropdown menus (`DropdownMenu`, the user menu, notification bell), and every form across the inventory (budget creation, transaction entry, account management, all four Settings screens, all Admin editing screens):
   - No keyboard trap anywhere.
   - Logical, predictable tab order matching visual reading order.
   - A visible focus indicator on every focusable element. `Sidebar`'s existing `focus-visible:ring-2 ring-offset-2 ring-offset-sidebar` pattern is the baseline every other interactive element must match — this phase's job is to extend that already-correct pattern everywhere it is currently missing, not invent a new one.
4. **Screen-reader smoke test** (NVDA or VoiceOver, per the CTO's tooling note) verified end-to-end on every flow `e2e-test-engineer.md`'s own charter already names: authentication (`/login`, both tabs and the Google OAuth entry point), dashboard (`/`), budget creation (`/budgeting`), transaction entry (`/transactions`, add/edit/split), account management (`/accounts`, add/edit/archive), reports (`/reports`, generate and download), goals (`/goals` and `/financial-goals`, create/edit), import (`/transactions`' CSV import), export (`/reports`' PDF download). Each flow must be operable start to finish by a screen-reader user, not merely "each individual control has a label" in isolation — the CTO's bar is a working flow, not a control-by-control checklist.
5. **Color-contrast audit covers every 4c accent-color preset crossed with both light and dark themes** — 6 presets (`blue`, `violet`, `emerald`, `amber`, `rose`, `teal`, per `src/app/globals.css`'s `[data-accent="..."]` rules) × 2 themes = 12 combinations, plus the no-accent-set default in both themes = 14 total combinations, every one of them audited, not just the shipped default. This directly closes Risk #43.
6. **Every form input has a programmatically associated label** (a real `<label for>`/`FormLabel` association, never placeholder-text-as-label) across every form in the inventory — the existing `Form`/`FormField`/`FormLabel` pattern already used in `/login` and elsewhere is the correct pattern to extend, not replace.
7. **Every icon-only interactive control has an accessible name** (`aria-label` or equivalent) — `Sidebar`'s collapsed icon-only nav items (`aria-label={item.label}`) and `TopNav`'s icon buttons (`aria-label="Open navigation menu"`, `aria-label="Open user menu"`) are the existing correct pattern; this AC requires every other icon-only control across the inventory (table row-action buttons, `DropdownMenuTrigger`s, the sidebar collapse toggle, close buttons on `Dialog`/`Sheet`) match it.
8. **Every data table's sort/filter/pagination controls, and every chart's data, remain operable and perceivable without relying on color alone** — e.g. Budgeting's over-budget indicator, Debt's payoff-comparison coloring, Bills' status treatment, and Calendar v2's bill-vs-payday distinction (which already commits to "color is never the sole distinguishing signal," per `calendar-v2.md` AC5) must each carry a non-color signal (icon, text label, pattern) wherever this audit finds one that doesn't yet.
9. **Landmark regions and heading structure are correct and consistent app-wide**: one logical `<main>` per authenticated route (already present via `(dashboard)/layout.tsx`'s `<main>`), a correct heading hierarchy per page (no skipped levels, no page with zero or multiple `<h1>`s), and `Sidebar`'s existing `aria-label="Primary"`/`aria-label="Main navigation"` pattern extended to any other landmark this audit finds missing one (e.g. Admin's own header/nav chrome, which currently has no equivalent).
10. **Newly-introduced Phase 5a structures meet this same bar from the start, not as a follow-up**: the new bottom-navigation component (see Responsive Capability below) must itself be fully keyboard-operable, carry correct `aria-current`/accessible names per item, and pass the same axe-core check as every other route's chrome — it is audited as part of this same pass, not exempted as "just shipped."

### Edge Cases

- **A modal/dialog (`Dialog`, `Sheet`) opens at the smallest supported viewport (< 640px)**: the dialog itself must never exceed the viewport's width/height in a way that clips its own content or its own close control — it scrolls internally if its content is taller than the viewport, but the dialog chrome (title, close button, primary action) remains reachable without the user needing to resize or rotate the device. This is a binding requirement, not an accepted degradation, since several of this app's most important flows (transaction entry, account creation, budget creation) are dialog-driven today.
- **Keyboard focus behavior when a `Sheet`/`Dialog` closes**: focus returns to the element that triggered it (e.g. closing the mobile nav `Sheet` returns focus to the hamburger trigger button; closing a "New Transaction" dialog returns focus to the button that opened it) — never left on a now-unmounted element, and never silently reset to the top of the page/`<body>`. This is the standard, expected screen-reader/keyboard-user behavior and is treated as a defect, not a nice-to-have, when violated.
- **An accent-color preset that turns out to fail contrast** (against either light or dark theme, at any of the 6 presets audited under AC5): **the spec requires fixing the preset's token value, never silently dropping or hiding that preset from the picker.** A user who already selected a failing preset before this audit ran must not have their saved preference become a defect the moment this phase ships a fix — the fix is a CSS custom-property adjustment to the same `[data-accent="..."]`/`.dark [data-accent="..."]` rule already defined in `globals.css`, not a product change to `customization.md`'s "5 to 8 curated options" requirement or a removal of user choice. This is consistent with the CTO's own Section 4 scoping ("a targeted token adjustment, not a rebrand").
- **A screen-reader announces a live, data-driven region** (a toast notification via `sonner`, an in-place-updating stat card, a table re-sorting): the update must be announced via an appropriate live region (`aria-live`), not silently changed with no assistive-technology signal — flagged explicitly since this class of dynamic update is easy to miss in a manual visual review and exists throughout this app's toast-notification and data-table patterns.
- **A long merchant/category name, bill name, or income-stream name inside an accessible name or `aria-label`**: the accessible name must still be the full, untruncated string (assistive technology reads the real value, not the visually-truncated one) even where the visible label is truncated with an ellipsis for layout reasons — visual truncation and accessible-name truncation are never the same decision.

## Capability: Responsive

### Acceptance Criteria

1. **Three named breakpoints, binding, matching Tailwind's own scale already in use throughout this codebase** (CTO-set, Section 3):
   - **Mobile**: `< 640px` (below Tailwind's `sm`)
   - **Tablet**: `640px – 1024px` (Tailwind's `sm` through just below `lg`)
   - **Desktop**: `≥ 1024px` (Tailwind's `lg` and above)
   No fourth scale, no per-feature custom breakpoint is introduced by this phase.
2. **Every route in the Route/Screen Inventory above is verified, at all three breakpoints, with**: no horizontal scroll of the page itself, no clipped or overlapping content, and no functionally unreachable control (a button rendered off-screen, a control only reachable by a hover state that doesn't exist on touch, a fixed-position element permanently covering another control). This is a full inventory pass, not a spot-check of a few representative screens — the CTO's Section 3 constraint is explicit on this point.
3. **Every data-heavy surface gets one explicit, documented mobile-treatment decision, decided once as a reusable pattern per surface type, not reinvented per feature** — resolved below, not left open:
   - **Transactions table**: **card-list fallback below the tablet breakpoint (`< 640px`); the existing `@tanstack/react-table`-driven table renders unchanged at tablet and desktop (`≥ 640px`).** Reasoning: Transactions is this product's single highest-interaction-frequency table (search, sort, filter, pagination, per-row actions including split/edit/delete/AI-suggestion review) — squeezing its existing column set (date, merchant, category, amount, account, notes/tags, actions) into a horizontally-scrolling strip on a 375px-wide screen would make its own row actions (the `MoreHorizontal` dropdown) difficult to reach reliably by touch, and horizontal scroll actively fights this AC's own "no horizontal scroll" bar for the page shell. A card-list layout (one card per transaction: merchant + amount prominent, category/account/date as secondary metadata, the existing row-action menu preserved as a per-card affordance) is this app's already-established pattern for "a data-dense row, reflowed for a narrow viewport," and is the correct fit for a surface this central to daily use.
   - **Reports**: **column-priority collapse.** Reports' own surface is a generation/download control (report type, period selector, a "Generate" action) plus, where content is inline-previewed, tabular figures — it is not a high-frequency interactive table the way Transactions is. Column-priority collapse (hide/deprioritize secondary columns first, keep the primary type/period/action controls always visible) keeps the generation workflow itself fully usable on mobile without the added complexity of a full card-list conversion for what is fundamentally a short, action-oriented form plus an occasional preview table.
   - **Analytics charts**: **horizontal-scroll-with-affordance**, not card-list and not column-priority collapse. Charts (Recharts-rendered bar/line/heatmap visualizations) are not tabular data that can be meaningfully "reflowed" into cards — a chart's value is its shape, which a card-list conversion would destroy. Each chart container becomes independently horizontally scrollable within its own card boundary (the page itself never scrolls horizontally, per AC2), with an explicit, visible affordance (e.g. a subtle scroll-shadow/gradient edge or a "swipe to see more" hint) so a user on mobile knows there's more chart to see rather than assuming the visible portion is the whole picture — this is the one surface type across this decision where "more content is available sideways" is itself real, useful information, unlike a data table's columns.
   - **Admin's user list / audit log**: **card-list fallback below tablet, same pattern as Transactions**, for the same underlying reason (`UserTable`'s email/name/signup-date/verification/last-active columns and `AuditLogTable`'s event/user/timestamp/outcome columns are both row-oriented account/event records, not chart data), plus one additional reason specific to Admin: this surface is used by a small, internal team, not end users at scale, so consistency with the already-justified Transactions pattern (one card-list convention, reused, not reinvented) is a stronger argument than any Admin-specific tuning would be — directly satisfying this AC's own "decided once as a reusable pattern... not reinvented per feature" requirement.
4. **Bottom navigation on mobile has an explicit, resolved relationship to the existing hamburger `Sheet` mobile sidebar — resolved below, in "Open Questions Resolved," not left ambiguous** (CTO-set, Section 3/Risk #42).
5. **Touch targets meet a 44×44px minimum** (standard WCAG/iOS/Android guidance, CTO-set) on every interactive control across the inventory — every button, table row-action trigger, form control, and nav item, at every breakpoint where touch is the plausible input method (mobile and tablet; desktop's mouse-driven targets are not held to this same physical-size bar, consistent with standard guidance).
6. **`Sidebar`'s existing three states — hidden below `md`, icon-only between `md` and `lg`, full-width at `lg`+ — are re-verified as correct at the tablet breakpoint specifically, not rebuilt.** Tablet (`640–1024px`) spans across `Sidebar`'s existing `md` (768px) icon-only transition point, so this phase's job on the sidebar itself is verification (does the icon-only band read correctly, are all icon-only nav items' `aria-label`s reachable and correct, does the collapse toggle remain usable) — not a new sidebar behavior, per the CTO's explicit "re-verified, not rebuilt" framing.
7. Every route confirmed against AC2 is additionally confirmed to preserve its own already-existing desktop functionality unchanged — this is an audit-and-complete pass, not a redesign; a route that already worked correctly at all three breakpoints before this phase is expected to still work identically after it, just now verified rather than assumed.

### Edge Cases

- **A long merchant/category/bill/income-stream name inside a mobile card-list layout** (Transactions, Admin's user/audit-log card-list fallback): truncates visually with an ellipsis and a `title`/tooltip or an accessible full-value affordance (see the Accessibility Capability's own "accessible name truncation is never the same decision as visual truncation" edge case above) — it never breaks the card's layout, overflows into a neighboring card, or forces horizontal scroll on the page.
- **A dialog/sheet at the smallest supported viewport**: covered under the Accessibility Capability's own edge case above (same underlying requirement, both structural and perceivable) — restated here so the Responsive capability's own Definition of Done can check it independently without cross-referencing.
- **A very long list rendered as a mobile card-list fallback (e.g. hundreds of transactions)**: pagination behaves identically to the desktop table's pagination — the card-list conversion changes layout, never the underlying paging/search/sort/filter behavior a user already relies on.
- **A chart's horizontal-scroll affordance (Analytics) on a device with no visible scrollbar** (most touch devices): the scroll-shadow/edge-gradient affordance from AC3 above must still be visible and correct even where the browser renders no persistent scrollbar chrome — this is exactly why an explicit affordance is required rather than relying on the browser's own scrollbar as the only signal.
- **The new bottom-navigation component at the tablet breakpoint**: bottom nav is a mobile-only (`< 640px`) pattern per its resolved role below; at tablet and above it does not render at all, and `Sidebar`'s icon-only/full states (AC6) are what a tablet/desktop user sees instead — there is no breakpoint at which both bottom nav and a visible sidebar compete for the same screen space.
- **Admin routes specifically**: Admin's own chrome (`app/admin/layout.tsx`'s header + `AdminNav` horizontal tabs) has no bottom-nav equivalent and is not in scope for one — Admin is internal team tooling, not a consumer-facing flow, and the CTO's Section 3 bottom-nav constraint is scoped to the app's ordinary (non-admin) navigation exactly as `Sidebar`/`NAV_SECTIONS` already is. Admin's own tab-based nav still must meet every other Responsive AC above (no horizontal scroll of the page shell, 44×44px touch targets, no clipped content) at all three breakpoints.

## Open Questions Resolved

The CTO's Section 5 explicitly left two questions for this spec to resolve rather than deciding them unilaterally. Both are resolved here, with reasoning, so Phase 5b's later spec does not have to re-litigate either one.

### (a) Reduced-motion scope: OS-level `prefers-reduced-motion` only — no persisted in-app override in this phase

**Resolution: 5a ships no reduced-motion handling of its own (that is entirely 5b's concern, since 5a introduces no animation), and this spec's answer for 5b's benefit is: ship OS-level `prefers-reduced-motion` support only in Phase 5b. Do not add a persisted in-app override field to `UserPreference` in either 5a or 5b.**

Reasoning:
1. **No demonstrated need exists yet.** This app has zero animation-adjacent user complaints or requests on record (there has been no meaningful animation to complain about — Framer Motion is used in exactly one component today, per the CTO's own Section 2 finding). Building a persisted override for a problem that hasn't been observed is exactly the speculative-infrastructure pattern this project's own precedent already rejects — the same reasoning Risk #28 used to reject a drag-and-drop widget-builder framework and full multi-currency support at 4c's kickoff: don't build the general/configurable version of a capability before a demonstrated need justifies it over the simpler, standard one.
2. **OS-level `prefers-reduced-motion` is the correct default mechanism, not a placeholder for something more.** It is the standard, well-understood, zero-configuration way a user expresses this preference once, at the operating-system level, and have it respected by every application on their device — including this one. A user who wants reduced motion in FinanceOS specifically already has the tool to get it (their OS accessibility settings), and respecting that signal centrally (per the CTO's `MotionConfig reducedMotion="user"`-style binding constraint in Section 3) is a complete, correct implementation of this requirement on its own terms — not a partial one that a second, in-app toggle would need to complete.
3. **A persisted override would be schema and product work this phase (5a) was never scoped for.** 5a introduces no new data model at all, per the CTO's own Section 4 out-of-scope list ("Any new data model or feature... is a schema question for the Solution Architect/Database Architect pass to size and for the CTO to confirm — not something decided unilaterally in this kickoff pass"). Answering "yes, persisted" here would size a `UserPreference` schema change for 5a's own architecture pass to carry, which is precisely the ambiguity the CTO flagged this question to avoid — better resolved now, cleanly, as "no," than left to surface mid-5a-architecture as an unplanned schema addition.
4. **If real demand later emerges** (a user whose OS-level setting is, for whatever reason, not the granularity they want inside just this one app), that is a genuinely new, small, well-scoped feature for a future phase — a single boolean field on `UserPreference`, following the exact precedent Customization's (4c) own preferences model already established for every other per-user display setting. Nothing about this decision forecloses that; it simply declines to build it speculatively now.

**Consequence for 5a's Solution Architect pass**: no schema sizing is needed for this question — the parenthetical in the CTO's Section 6 milestone list ("Database Architect only if the reduced-motion-override question above resolves to 'yes, persisted'") does not apply. No Database Architect participation is required for 5a on this question's account.

### (b) Bottom navigation's relationship to the existing hamburger `Sheet` sidebar: a distinct, narrower role alongside it — it does not replace the sidebar

**Resolution: bottom navigation is a new, mobile-only (`< 640px`), fixed, 4–5-item quick-access bar for this product's most-used routes. It does not replace the existing hamburger-triggered `Sheet` mobile sidebar (`components/shared/top-nav.tsx`'s `Sheet`/`SheetTrigger`, rendering `<Sidebar mobile />`), which remains the complete navigation surface for every route in the inventory above, reached via the hamburger trigger exactly as it works today.**

Reasoning:
1. **The two serve genuinely different jobs, not a redundant one.** The existing hamburger `Sheet` sidebar is already a complete, working, full-route navigation surface — every item in every `NAV_SECTIONS` group (Dashboard, Accounts, Transactions, Budgeting, Goals, Bills, Income, Calendar, Debt, Investments, Analytics, Reports, Financial Goals, Health Score, and all three Settings pages) is reachable through it today, and Risk #42 confirms this mechanism is already shipped and working, not a gap. A bottom nav that duplicated this same complete list would be, verbatim, "a second, competing mobile-navigation mechanism" — the exact violation of this project's "avoid duplication" standard the CTO's own kickoff pass flagged as the risk to resolve (Risk #42), not a feature to build twice. A bottom nav scoped instead to a small, fixed subset of the most-used routes is not a competing mechanism — it is a faster path to the small number of destinations a mobile user reaches for most often, with the full hamburger sidebar remaining the answer to "everything else."
2. **This is the standard, well-understood mobile-navigation pattern this class of app already resembles.** Consumer finance apps (and mobile apps generally) commonly pair a bottom nav of 4–5 top-level destinations with a secondary "more"/menu affordance for the full route list — exactly the two-tier structure this resolution produces (bottom nav for the few, hamburger `Sheet` for the all). This is not a novel pattern this spec is inventing; it is the reason "bottom navigation on mobile" was named as a distinct, additive capability in the original Phase 5 stub in the first place, rather than "replace the sidebar with a bottom nav."
3. **A full-replacement bottom nav is a worse fit for this app's actual route count.** This inventory lists 24 distinct routes across 4 nav sections (plus Admin, out of scope for bottom nav per the Responsive Capability's own edge case above). A bottom nav large enough to hold even a meaningful fraction of that list would violate the very touch-target-size and no-clipped-content bars this same Responsive Capability sets (AC5, AC2) — bottom navs are only usable at 4–5 items. Scoping it narrowly is not a compromise; it is the only version of "bottom navigation" that can actually satisfy this phase's own other binding constraints.
4. **The specific route set is a Frontend Lead implementation call, not fixed here** — this spec's product requirement is the *relationship* (additive, narrow, alongside the hamburger sidebar, never a replacement) and the *count* (4–5 items, informed by AC5's touch-target math on however wide a bottom-nav bar this app's smallest supported viewport allows), not the literal list of which 4–5 routes. A reasonable starting set, illustrative only, would be Dashboard, Transactions, Budgeting, Bills or Calendar, and a "More" entry that opens the existing hamburger `Sheet` — giving mobile users a fast path to daily-use destinations while keeping the hamburger sidebar as the one, single, complete source of truth for full navigation, never duplicated.
5. **This resolution is consistent with, and reuses, the existing sidebar's own active-state and accessibility patterns** (`aria-current="page"`, `aria-label` per item, `focus-visible:ring-2` treatment) — the new bottom-nav component must match those, per the Accessibility Capability's AC10 above, rather than inventing a second visual/interaction language for wayfinding.

**Consequence for 5a's Solution Architect pass**: the bottom-navigation component's code boundary and its reuse relationship to `Sidebar`'s existing `NavItem`/`NavSection` types (e.g. whether it's a filtered subset of the same `NAV_SECTIONS` data or its own small, separately-maintained list) is that pass's call, per the CTO's Section 6 milestone 3 — this spec fixes only the product-level relationship (additive, narrow, non-replacing) resolved above.

## Definition of Done

**Accessibility:**
- Automated axe-core coverage runs against all 24 routes in the inventory (plus shared chrome), with zero critical/serious violations at gate time; every accepted moderate/minor finding is a named, owned backlog item with an assigned owner, not silently dropped.
- Full keyboard-only navigation verified, by test where automatable and by manual pass otherwise, across every interactive surface named in AC3 above — no keyboard trap, correct tab order, visible focus indicator matching `Sidebar`'s existing pattern, confirmed on every route.
- Screen-reader smoke test (NVDA or VoiceOver) completed and passing for all nine flows named in AC4, each verified end-to-end, not control-by-control.
- Color-contrast audit completed and passing for all 14 accent-preset × theme combinations (6 presets × 2 themes + default × 2 themes) named in AC5; any failing combination has its token fixed (never its preset removed), per the Edge Cases section above.
- Every form input across the inventory verified to have a programmatically associated label; every icon-only control verified to have an accessible name, confirmed by the automated axe-core pass plus manual spot-verification of dynamically-rendered controls (row-action menus, toast notifications) axe-core's static-page crawl may not fully exercise.
- The new bottom-navigation component (Responsive Capability) passes this same full Accessibility Definition of Done — not shipped ahead of or exempted from it.
