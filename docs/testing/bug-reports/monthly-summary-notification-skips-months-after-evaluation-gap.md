# Bug Report: Monthly Summary notification only ever checks the single most-recent `MonthlySummary` row — an evaluation gap spanning more than one newly-generated month permanently drops the notification for the older month(s), with no way to recover

## Severity
**Medium** — not a crash or a security issue, but a silent, permanent, unrecoverable violation of the feature's own Acceptance Criterion 1 ("Fires once per user, once per calendar month, when that month's `MonthlySummary` row exists with a non-null narrative") for any month caught in an evaluation gap. Requires either a real operational gap (a cron outage/deploy issue spanning a month boundary) or a sufically inactive user (no lazy poll for 2+ months) to manifest, but is straightforward to construct deterministically in a test, and the notification lost is exactly the kind of "come back and look at this" nudge — the Monthly Summary card — email delivery exists specifically to reach a user who isn't opening the app, which is also the exact population most likely to hit this gap.

## Component
`src/features/notifications/server/triggers/monthly-summary-trigger.ts` lines 44-58 (`evaluateMonthlySummaryTriggers`)
`src/features/dashboard/server/monthly-summary.ts` lines 816-822 (`getMostRecentSummary`)

## Summary
`evaluateMonthlySummaryTriggers` calls `getMostRecentSummary(userId)` — a `findFirst` ordered `desc` by `month`, returning **only the single latest** `MonthlySummary` row for that user (lines 816-822 of `dashboard/server/monthly-summary.ts`) — and, if its `narrative` is non-null, attempts to create exactly one `MONTHLY_SUMMARY_READY` notification keyed to that one row's id. The file's own doc comment (lines 19-28) is explicit about *why*: checking every past month's row "on this trigger's first-ever evaluation for a long-tenured user would fire a burst of stale 'ready' notifications" — a deliberate anti-flood decision for a **brand-new user's first-ever evaluation**.

That reasoning only covers the *launch-day backfill* case. It does not hold for **ongoing** operation: this same "most-recent-row-only" query runs on **every** evaluation pass (both the lazy per-user poll and the `evaluate-notifications` cron sweep), for the entire lifetime of the feature, not just once at launch. If evaluation for a given user does not happen at all between two consecutive months' `MonthlySummary` generations — e.g. the `evaluate-notifications` cron has an outage spanning more than one month boundary, or the user simply doesn't open the app (no lazy poll) for more than a month while also (for whatever reason) not being reached by the cron sweep for that same stretch — then by the time evaluation next runs, `getMostRecentSummary` only sees the **latest** of the two-or-more newly-generated rows. The older month's row is never independently checked, never gets its own `createNotificationIfNew` attempt, and therefore **never** produces a notification — not delayed, not deduplicated, permanently absent. There is no backfill sweep, no "catch up on skipped months" path anywhere in this trigger or its caller.

This is a strictly different failure mode than the dedup guarantee the design doc is actually confident about (`@@unique([monthlySummaryId, type])` correctly prevents a *second* notification for a month already notified, including across `regenerateMonthlySummary` calls, which reuse the same row id) — the bug here is the **first** notification for a given month never being attempted in the first place, for any month that isn't the most-recent one at the moment evaluation resumes.

## Reproduction Steps
1. Seed a user with a `MonthlySummary` row for month `M1` (e.g. `2026-05`), narrative non-null, and confirm no `MONTHLY_SUMMARY_READY` notification exists for it yet (simulating: the cron/monthly-summary job generated it, but no evaluation pass has run since).
2. Before any evaluation (`ensureNotifications`/`evaluateMonthlySummaryTriggers`) runs for this user, seed a **second** `MonthlySummary` row for the next month, `M2` (e.g. `2026-06`), narrative also non-null — simulating a second month closing/generating while the user remained unevaluated (a multi-month cron gap, or an inactive user whose lazy poll also didn't fire in between).
3. Now run `evaluateMonthlySummaryTriggers(userId)` (or trigger it via `ensureNotifications`/a `GET /api/notifications` poll) for the first time.
4. Observe: `getMostRecentSummary` returns only `M2`'s row (`orderBy: { month: "desc" }`, `findFirst`); `createNotificationIfNew` is attempted only for `M2`.
5. Query `Notification` rows for this user of type `MONTHLY_SUMMARY_READY`: exactly one exists, for `M2`. `M1` never received one, and — since the trigger's only signal is "narrative exists and no notification exists yet for it," but the trigger never even looks at `M1`'s row again once a newer row exists — running the evaluator any number of additional times afterward still never creates one for `M1`. The gap is permanent.
6. Unit-test-level equivalent: `monthly-summary-trigger.test.ts`'s own mocked coverage only ever supplies a single `getMostRecentSummary` return value per test and asserts `createNotificationIfNew` is called with that one row's id — there is no test constructing two real, unnotified rows to show the older one is silently skipped, which is exactly the gap this report identifies.

## Expected Behavior
Per notifications-v2.md's Monthly Summary Acceptance Criterion 1, the trigger should fire once **per calendar month** that has a `MonthlySummary` row with a non-null narrative — every such month, not only whichever one happens to be most recent at the moment evaluation next runs. The stated anti-flood concern (a long-tenured user's *very first* evaluation ever) is a real, narrower problem that deserves its own bounded solution (e.g. only backfill/notify for months within some recent window on a user's first-ever evaluation, mirroring Large Purchase's own explicit recency-window precedent for the identical class of concern) — not a blanket "only ever look at the single latest row" rule that also silently discards legitimate, never-yet-notified months during ordinary ongoing operation.

## Actual Behavior
`evaluateMonthlySummaryTriggers` structurally cannot detect or notify for any `MonthlySummary` row other than the single most-recent one at evaluation time. Any month whose row was generated while a strictly newer month's row was *also* generated before the next evaluation pass runs for that user is permanently skipped — no notification, no error, no record that anything was missed, and no remediation path short of a manual/administrative intervention outside this trigger's own code.

## Suggested Owner
Backend Engineer, `src/features/notifications/server/triggers/monthly-summary-trigger.ts` (evaluator logic) and `src/features/dashboard/server/monthly-summary.ts` (`getMostRecentSummary`, or a new bounded "months since last notified" read this trigger would need instead) — the fix likely needs a small, explicitly-bounded window (mirroring Large Purchase's own `RECENCY_WINDOW_DAYS` precedent) rather than a genuinely unbounded full-history sweep, to keep the original anti-launch-flood intent intact while closing this gap.
