# Bug Report: Dashboard's shared `budgetHealthScorePromise` — a single `getBudgetHealthScore` failure now crashes the entire Dashboard (no error boundary), and the "load time is unaffected" performance claim is false

## Severity
**High** (failure mode: an unhandled, uncaught DB error on one deterministic, non-AI query takes down every card on the page, including cards with no relation to Budgeting or the Health Score, with no graceful degradation and no error boundary anywhere in this route segment) / **Medium** (the latency-neutrality claim, on its own, if the failure risk is judged acceptable).

## Component
`src/app/(dashboard)/page.tsx` lines 105, 118-151 (`budgetHealthScorePromise`, its two `Promise.all` usages)
`src/features/budgeting/server/service.ts` lines 314-344 (`getBudgetHealthScore` — no internal try/catch, by explicit design)
`src/features/financial-health-score/server/service.ts` lines 269-316 (`getFinancialHealthScore`'s `precomputedBudgetHealthScore` doc comment, Finding 3)

## Summary
`app/(dashboard)/page.tsx` creates `budgetHealthScorePromise = getBudgetHealthScore(user.id, currentMonth)` once (line 105), then uses it **twice** inside the same `Promise.all` array: directly as the `budgetHealthScore` entry (line 124), and again via `budgetHealthScorePromise.then((score) => getFinancialHealthScore(user.id, new Date(), score))` (lines 148-150) for the `financialHealthScore` entry. The stated rationale (lines 97-104, 138-147) is purely a performance one: avoid `getFinancialHealthScore`'s internal `gatherBudgetAdherenceComponent` re-fetching the same Budget Health Score independently.

**Confirmed: `getBudgetHealthScore` has no try/catch of its own** (`budgeting/server/service.ts` line 314 onward) — its own sibling function's doc comment (`financial-health-score/server/service.ts` lines 262-267) states plainly that "an actual thrown error (e.g. a transient DB failure) is left to propagate uncaught, matching every other plain deterministic read in this codebase." If `buildBudgetMonthView` (which `getBudgetHealthScore` calls internally) throws — a transient Postgres connection blip, a pool-exhaustion error, anything — `budgetHealthScorePromise` rejects.

Because that single promise is referenced from **two** entries in the outer `Promise.all` (the direct reference, and the `.then()`-derived promise, which re-throws the same rejection since no `onRejected` handler is supplied), and `Promise.all` rejects as soon as **any** one of its array entries rejects, the **entire** `Promise.all` covering all ten Dashboard data fetches (`netWorth`, `monthlySummary`, `spendingByCategory`, `monthlyTrends`, `budgetSummary`, `budgetHealthScore`, `defaultRangeResolution`, `mostRecentMonthlyRecap`, `monthlyRecapHistory`, `financialHealthScore`) rejects. There is no `try`/`catch` around this `Promise.all` in `page.tsx`, and — confirmed via `Glob` — **no `error.tsx` exists for the `(dashboard)` route segment or its `page.tsx`, nor a root `app/error.tsx`/`global-error.tsx`** (the only `error.tsx` in the whole `app/` tree is `app/(dashboard)/analytics/error.tsx`). A rejection here falls through to Next.js's bare, unstyled default error handling for the entire route — Net Worth, Monthly Income/Expenses, Cash Flow, Savings Rate, every chart, and the Monthly Summary card all fail to render, none of which have anything to do with Budget Health Score.

**The performance-neutrality claim is also inaccurate.** Before this reorder, `getFinancialHealthScore(user.id, new Date())` (no `precomputedBudgetHealthScore` argument) would have started running — including its own internal `Promise.all` across `gatherDebtToIncomeComponent`, `gatherSavingsRateComponent`, `gatherBudgetAdherenceComponent` (its own independent `getBudgetHealthScore` call), and `gatherNetWorthTrendComponent` — **concurrently** with the page's own `getBudgetHealthScore` call, both as independent, immediately-started entries in one flat `Promise.all`. After this change, `getFinancialHealthScore` is chained behind `budgetHealthScorePromise` via `.then()` — meaning `gatherDebtToIncomeComponent`, `gatherSavingsRateComponent`, and `gatherNetWorthTrendComponent` (three DB-bound reads entirely unrelated to Budget Health Score) do not even **begin** executing until `budgetHealthScorePromise` has fully resolved. The comment at lines 143-147 claims this "only sequences `getFinancialHealthScore` behind the single `getBudgetHealthScore` call it needs anyway... the page's overall load time (bounded by the slowest entry here) is unaffected" — but this is only true if `getBudgetHealthScore` is faster than every other entry in the outer `Promise.all` combined with `getFinancialHealthScore`'s own remaining three components. If `getBudgetHealthScore` is itself slow (e.g. a large category count, or DB contention), overall Dashboard load time is now `duration(getBudgetHealthScore) + max(duration(debtToIncome), duration(savingsRate), duration(netWorthTrend))` for that portion of the page — strictly worse than the prior `max(...)`-only bound across all of them as true siblings.

## Reproduction Steps
1. Instrument/mock `buildBudgetMonthView` (or the underlying Prisma call it uses) to throw on the current month for a given user — simulating a transient DB error (e.g. connection reset), reproducible in a unit/integration test by mocking `db` to reject once.
2. Load `/` (the Dashboard) as that user.
3. Observe: `budgetHealthScorePromise` rejects. Both its direct `Promise.all` entry and the `.then()`-derived `financialHealthScore` entry reject.
4. Observe: the outer `Promise.all` in `DashboardPage` rejects; the `await Promise.all([...])` throws, uncaught, inside the Server Component.
5. Observe: Next.js falls back to its default error handling for this route (no local/root `error.tsx` exists to catch it) — the entire Dashboard page fails to render, including Net Worth, Income/Expenses, Cash Flow, Savings Rate, Spending by Category, Income vs. Expense, Monthly Trends, Net Worth History, and the Monthly Summary card — none of which depend on Budget Health Score data at all.
6. Separately, to confirm the latency claim: instrument `getBudgetHealthScore` with an artificial delay (e.g. 2s) and `gatherDebtToIncomeComponent`/`gatherSavingsRateComponent`/`gatherNetWorthTrendComponent` with no delay. Compare total Dashboard server-render time against reverting to two independent (non-`.then()`-chained) calls — the chained version's total time includes the full 2s delay serialized in front of `getFinancialHealthScore`'s remaining component gathers, whereas the unchained version does not.

## Expected Behavior
A transient failure in one deterministic, non-AI query (Budget Health Score) should not cascade into an uncaught, whole-page failure for entirely unrelated Dashboard cards — consistent with this codebase's own stated principle (restated in multiple Phase 4a component doc comments) that "every metric degrades independently... one sparse/failing metric never blanks out the other[s]." The doc comment's specific performance claim ("the page's overall load time... is unaffected") should hold under a slow (not just failing) `getBudgetHealthScore` call.

## Actual Behavior
Any thrown error from `getBudgetHealthScore` propagates, uncaught, through both of its two `Promise.all` consumers simultaneously, rejecting the single `Promise.all` that gates the entire Dashboard's render with no error boundary in this route segment to contain the blast radius — a strictly page-wide failure mode for a query that used to (before Phase 4a) only affect its own Budget Health Score badge in isolation (a `null` return, not a thrown error, per that component's own already-existing "renders its own 'Not enough data yet' state" contract — the actual failure mode being described here is specifically an *uncaught exception*, which neither `getBudgetHealthScore` nor `getFinancialHealthScore` guards against, and which the shared-promise wiring now delivers to two consumers off one unhandled rejection instead of two). Additionally, the sequencing introduced by `.then()` measurably adds to worst-case page load time whenever `getBudgetHealthScore` is slow, contradicting the change's own stated performance rationale.

## Suggested Owner
Backend Engineer / Performance Engineer, `src/app/(dashboard)/page.tsx` (the shared-promise wiring and absent error boundary) and `src/features/budgeting/server/service.ts`/`src/features/financial-health-score/server/service.ts` (whether `getBudgetHealthScore` should itself catch transient errors, matching the "unavailable"/`null`-on-failure convention every AI-backed feature in this same codebase already follows, rather than being the one plain deterministic read left to propagate uncaught). Also flag to whoever owns route-level error handling: no `error.tsx` exists for `(dashboard)/page.tsx` or the segment root, unlike `(dashboard)/analytics/error.tsx`.
