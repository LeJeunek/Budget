# Bug Report: An already-mounted Phase 5b motion primitive that captured `prefers-reduced-motion: reduce` at mount never resumes animating after the user turns that OS preference back off mid-session — `useReducedMotion()` is not actually reactive, contrary to the architecture doc's own claim

## Severity
**Medium** — does not crash anything and does not violate the safety-critical direction of Reduced-Motion Foundation AC4 (a user who turns reduced-motion **on** mid-session while an already-mounted component is visible does get an instant, correctly-suppressed result — see Reproduction Steps for why, and note this is the direction that actually matters for a vestibular-sensitivity user's comfort/safety). But it is a real, reproducible violation of AC4's own explicit, binding wording for the opposite direction: turning the OS preference **off** mid-session (e.g. a user who enabled reduced-motion to get through a moment of discomfort, then disables it again) leaves every already-mounted Phase 5b primitive permanently stuck in its reduced (instant, non-animated) state for the rest of that page's lifetime — the polish this whole phase exists to add never returns without a manual reload, exactly the "requiring a manual refresh" case AC4 explicitly rules out. Because the underlying mechanism (`components/shared/motion/use-reduced-motion.ts`) is the one canonical hook every Phase 5b primitive is built to call (per the technical design doc's own §1.1 "every new primitive... branches explicitly on the same one hook"), this is a systemic property of the shared mechanism, not a one-off miswiring in a single consumer.

**Related, but distinct, finding:** `docs/testing/bug-reports/reduced-motion-not-honored-on-first-page-load-animated-number-progress-ring.md` (filed separately) covers a first-load timing race where `AnimatedNumber`/`ProgressRing` briefly animate despite `reduce` already being active *before* navigation even starts. That is a mount-time race in a fresh page load. This report is about a different moment entirely — an already-mounted, already-settled component's behavior *after* a live, mid-session OS preference change — and per `docs/testing/e2e/reduced-motion-report.md`'s own "What this run does NOT cover" section, the reactive mid-session half of AC4 was explicitly left unexercised by that E2E pass; this report closes that gap.

## Component
- `src/components/shared/motion/use-reduced-motion.ts` — a bare re-export of `framer-motion`'s own `useReducedMotion` hook.
- `node_modules/framer-motion/dist/es/utils/reduced-motion/use-reduced-motion.mjs` (installed version, confirmed by direct read) — the actual implementation being re-exported.
- `node_modules/motion-dom/dist/es/render/utils/reduced-motion/{index,state}.mjs` — the module-level `prefersReducedMotion`/`hasReducedMotionListener` refs this hook reads from.
- Every consumer that branches explicitly on this hook to compute an animation prop (`initial`/`exit`/`transition.duration`, or a chart's `isAnimationActive`) is affected by construction, per the technical design doc's own inventory: `components/shared/motion/expandable-card.tsx` (confirmed live, see Reproduction Steps), `animated-number.tsx`, `fade-in.tsx`/`page-transition.tsx`, `chart-animation.ts`, and `components/ui/progress.tsx`.
- `src/app/providers.tsx` — mounts `<MotionConfig reducedMotion="user">`, whose own doc comment makes the specific, now-confirmed-incorrect claim this report disproves (see Summary).

## Summary
`docs/architecture/phase-5b-technical-design.md` §1.1 states, as the stated reason no project-owned `matchMedia` hook was built: *"Framer Motion's own `useReducedMotion` hook... subscribes to the `matchMedia` query's `change` event internally and re-renders every consumer automatically."* This is factually incorrect for the installed version (`framer-motion`, confirmed via `npm ls`/direct source read). The actual implementation:

```js
// node_modules/framer-motion/dist/es/utils/reduced-motion/use-reduced-motion.mjs
function useReducedMotion() {
    !hasReducedMotionListener.current && initPrefersReducedMotion();
    const [shouldReduceMotion] = useState(prefersReducedMotion.current);
    // ...
    // TODO See if people miss automatically updating shouldReduceMotion setting
    return shouldReduceMotion;
}
```

`initPrefersReducedMotion()` does set up a real, module-level `matchMedia` "change" listener (`motion-dom`'s `state.mjs`) that keeps the **raw ref** `prefersReducedMotion.current` in sync with the live OS preference for the lifetime of the page. But each component's own `useReducedMotion()` call captures that ref's value **once**, via `useState`'s initializer, at the moment that specific component instance first mounts — React does not re-invoke a `useState` initializer on re-render, and nothing here ever calls the corresponding setter. So an already-mounted component's `shouldReduceMotion` is frozen at whatever the preference was when it first mounted, for as long as it stays mounted, regardless of how many times the OS preference subsequently changes or how many times the component re-renders for unrelated reasons. The hook's own upstream source literally flags this as a known, unresolved gap (`// TODO See if people miss automatically updating shouldReduceMotion setting`).

This directly contradicts Reduced-Motion Foundation AC4: *"The preference is honored reactively, not just at initial page load... every subsequently-triggered animation in the app respects the new setting immediately, without requiring a manual refresh."*

**Why the "enable reduce mid-session" direction still appears to work correctly** (confirmed empirically, see Reproduction Steps): `MotionConfig`'s own `reducedMotion="user"` mechanism operates through a second, lower-level path (`use-visual-element.mjs` threading `reducedMotionConfig` into each `motion.*` component's internal `VisualElement` at DOM-node-creation time) that appears to independently, correctly suppress in-flight/new animations once the live preference flips to `reduce` — this acts as a genuinely reactive kill-switch layered on top of whatever explicit `transition`/`initial` props a component's own (stale) `useReducedMotion()` branch computed. But this kill-switch only ever *suppresses*; it cannot *restore* an animation a component's own explicit branch has hard-coded to `duration: 0` / no `initial` offset from a stale `true` reading. So the **moment a component first mounts with `reduce` active, it is permanently stuck non-animating for its remaining lifetime**, even after the OS preference reverts to `no-preference` — MotionConfig's own reactivity has nothing left to re-enable, since the explicit per-primitive prop already zeroed the duration.

## Reproduction Steps
1. Sign in as the seeded e2e user, set viewport to `375×800` (so `DataTableCardList`'s expandable cards render).
2. `await page.emulateMedia({ reducedMotion: "reduce" })`, then `page.goto("/transactions")`. Wait for the "Show more" trigger to be visible (this is Transactions' 5a `DataTableCardList` row, now carrying Phase 5b's `ExpandableCard` for its `tags`/`notes` columns).
3. `await page.emulateMedia({ reducedMotion: "no-preference" })` — flips the OS-level preference **without reloading the page**. Confirmed via `window.matchMedia("(prefers-reduced-motion: reduce)").matches` reporting `false` immediately after.
4. Click the "Show more" trigger and sample the disclosed region's `getBoundingClientRect().height` at 12 points over ~200ms.
5. **Result: the region jumps straight to its final height (flat `54, 54, 54, ...` from the very first sample) — no growth animation at all**, even though the OS preference is now confirmed `no-preference` and `EXPANDABLE_CARD_DURATION_MS` (250ms) should produce a visible ramp (confirmed by a same-page baseline: mounting fresh under `no-preference` throughout produces a clear ramp, `30.5 → 37.6 → 44.1 → 47.1 → 49.8 → 53.1 → 53.9 → 54, 54...`).
6. Reload the page (still under `no-preference`) and repeat step 4 on the freshly-mounted component: **now it animates correctly** (`7.3 → 12.9 → 12.9 → 17.9 → 17.9 → 22.9 → 22.9 → 27.4 → 27.4 → 35.8 → 35.8 → 39.6`), proving the underlying mechanism and duration constant are otherwise sound — only the already-mounted instance is stuck.
7. A DOM-identity marker (`element.__customProp`) set on the row's `<li>` before the toggle was confirmed still present immediately before **and** after the click in step 4, ruling out an intervening remount (e.g. a query refetch replacing the row) as an alternative explanation.
8. For contrast, the reverse direction was also verified: mount under `no-preference`, toggle to `reduce` mid-session, then expand — the region is (correctly, if perhaps coincidentally per the mechanism above) instant, matching a fresh `reduce`-from-the-start baseline. This direction is not the bug being reported.

## Expected Behavior
Per Reduced-Motion Foundation AC4, an OS-level `prefers-reduced-motion` change while FinanceOS is open in a tab should be honored "immediately, without requiring a manual refresh" for "every subsequently-triggered animation in the app" — in both directions. A user who disables reduced-motion mid-session should see any subsequently-triggered `ExpandableCard` reveal, `AnimatedNumber` count-up, chart entrance/update, or page-transition fade resume its normal animated behavior, not remain frozen in the instant/no-animation state their earlier, since-reverted preference produced.

## Actual Behavior
Every already-mounted consumer of `components/shared/motion/use-reduced-motion.ts` that first mounted while `prefers-reduced-motion: reduce` was active remains permanently stuck rendering instant, non-animated state changes for the rest of that page's lifetime, even after the OS-level preference is changed back to `no-preference` — confirmed live for `ExpandableCard`; by construction (identical hook, identical explicit-branch pattern per the technical design doc's own description) this equally affects `AnimatedNumber`'s tween-vs-snap branch, `useChartAnimationProps()`'s `isAnimationActive` gate (for a chart whose own React component re-renders without remounting, e.g. an update-in-place data change), and `FadeIn`/`PageTransition` for any mount that isn't naturally remounted by other means (page transitions specifically are largely shielded from user-visible impact because `(dashboard)/template.tsx` remounts fresh on every navigation, incidentally re-reading the live preference each time — but any 5b primitive that persists across a data update without a full remount is exposed).

## Suggested Owner
Solution Architect / UI Component Engineer, `src/components/shared/motion/use-reduced-motion.ts`. The re-export's own justification (`§1.1`'s "both this hook and the root `<MotionConfig reducedMotion="user">`... can never disagree with each other") assumed a reactive upstream hook that the installed `framer-motion` version does not actually provide — worth confirming against `framer-motion`'s own changelog/issue tracker whether a newer major version fixes this (the TODO comment suggests it was still open at the time this dependency was installed), and if not, replacing this file's blind re-export with a thin wrapper that adds the one missing piece itself (e.g. `useSyncExternalStore` subscribed to the same `matchMedia` query, or a `useEffect` that subscribes to `change` and calls a local `setState`) — while still deferring the actual OS-preference-reading logic to `motion-dom`'s existing `prefersReducedMotion` ref/listener plumbing rather than standing up a second, independent `matchMedia` subscription, preserving the original file's own "avoid duplication" rationale. Also worth updating `providers.tsx`'s doc comment, which repeats the same now-disproven claim.
