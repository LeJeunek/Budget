# Bug Report: MonthlySummaryCard's main display never re-syncs to fresh Server Component data after `router.refresh()` — can contradict its own "View history" dialog for the same month

## Severity
**Medium-High** — same root cause class as the Spending Insights period-switch bug (a `useState(prop)` seed that's never resynced), but here reachable via a realistic concurrency scenario this codebase's own rate-limiting design explicitly anticipates (concurrent/racing generation attempts for the same `(userId, month)` key), and it produces a self-contradicting UI: the card's main body and its own "View history" dialog can show two different narratives for the *same* month on the *same* page load.

## Component
`src/features/dashboard/components/monthly-summary-card.tsx` (`MonthlySummaryCard`)
Rendered from: `src/app/(dashboard)/page.tsx` lines 287-290 (`<MonthlySummaryCard summary={mostRecentMonthlyRecap} history={monthlyRecapHistory} />`)
Server logic: `src/features/dashboard/server/monthly-summary.ts` (`regenerateMonthlySummary`, `getMostRecentSummary`, `getSummaryHistory`)

## Summary
`MonthlySummaryCard` seeds its displayed recap via `const [current, setCurrent] = useState(summary)` (line 62). As with `SpendingInsightsWidget`, this initializer only runs on first mount — a later `summary` prop change (from a `router.refresh()`-triggered Server Component re-render) is never applied to `current`, since there's no `key` prop distinguishing instances and no effect syncing the two. The card's main body (title + narrative) is driven entirely by `current`. The "View history" dialog, by contrast, reads the `history` prop **directly** in JSX (line 104: `{history.map((entry) => ...)}`) — a fresh prop, correctly reflecting whatever the latest `router.refresh()` fetched, with `getSummaryHistory` (`monthly-summary.ts` lines 822-828) including the current/most-recent month's own row as `history[0]` (same `orderBy: { month: "desc" }` as `getMostRecentSummary`).

This means the two are on two different data-freshness contracts within the same component: `current` is "whatever was true at mount, plus whatever this card's own `handleRegenerate` explicitly wrote to local state," while `history` is "always whatever the last Server Component render produced." Any `router.refresh()` that changes the current month's row *without* this card's own `handleRegenerate` being the one to have called `setCurrent` first will desynchronize them.

`handleRegenerate` (lines 65-84) demonstrates the concrete case: on a **rate-limited** or otherwise-still-unavailable regenerate attempt (`response.data.status !== "ok"`), the code does *not* call `setCurrent` (only the `"ok"` branch does), but **unconditionally** calls `router.refresh()` afterward regardless of branch. Combined with this codebase's own documented per-key concurrency design (`monthly-summary.ts`'s `claimGenerationSlot`/`MIN_REGENERATE_INTERVAL_MS`, explicitly built to arbitrate races between the monthly cron and a manual regenerate for the same `(userId, month)` key), the following is directly reachable:

## Reproduction Steps
1. User's most-recently-completed month has a `MonthlySummary` row with `narrative: null` (a prior generation attempt — cron or manual — failed). `MonthlySummaryCard` mounts showing "Summary not available for `<Month>`" with a "Try again" button, and the "View history" dialog's entry for that same month shows the identical "Summary not available for `<Month>`." message (both sourced from the same DB row at this point — consistent).
2. User clicks "Try again" (`handleRegenerate`). This calls `regenerateMonthlySummary({ month })`, which runs `attemptGenerationForUserMonth` → `claimReasoningModelGenerationSlot` → `claimGenerationSlot`.
3. Concurrently (e.g. this click happens to land within moments of the monthly cron's own `generateMonthlySummariesForAllUsers` invocation for this same user/month, or the user has a second tab open that already regenerated this month a moment earlier — both explicitly anticipated races per this file's own `claimGenerationSlot` doc comment), **another** attempt for the exact same `(userId, month)` key wins the atomic claim first and successfully persists a real narrative to the DB.
4. This click's own `attemptGenerationForUserMonth` call loses the race: `claimGenerationSlot`'s conditional `updateMany` affects 0 rows (the other attempt already bumped `generatedAt`), so `claimed = false`, and `regenerateMonthlySummary` returns `{ rateLimited: true, result: { status: "unavailable" } }`.
5. Back in the client, `response.success` is `true` (the Server Action itself succeeded; `rateLimited` only affects the outer `ApiResult`'s success flag — check `src/features/dashboard/server/actions.ts`'s `regenerateMonthlySummary` wrapper if `rateLimited` is mapped to `response.success = false`; either way, whichever branch runs, `setCurrent` is **not** called for the `unavailable`/rate-limited case) → `toast.error("Summary isn't available right now — try again later.")` fires — **a false statement**, since a summary was, in fact, just generated successfully by the concurrent attempt in step 3 — and (assuming the success path) `router.refresh()` still runs.
6. `router.refresh()` re-fetches `mostRecentMonthlyRecap`/`monthlyRecapHistory` from the DB — now correctly showing the concurrently-generated narrative. The new `summary` prop reaching `MonthlySummaryCard` **is** the fresh, populated recap. But `current` (local state) is never updated from it — the main card body keeps showing "Summary not available" and the "Try again" button.
7. User clicks "View history" — the dialog (reading `history` directly, freshly re-fetched) shows the **correct, populated** narrative for this exact month, directly contradicting what the main card body above it is still displaying for the same month.
8. This divergence persists indefinitely (surviving any number of further `router.refresh()` calls elsewhere on the page) until a hard page reload fully remounts the component.

## Expected Behavior
The main card body and the "View history" dialog should never disagree about the same month's content on the same page load; both should reflect the most recent successful `router.refresh()`'s data, the same way every other prop-driven part of this Server-Component-first codebase behaves.

## Actual Behavior
`current` (and therefore the card's title, narrative text, and "Try again" affordance) is only ever updated by this card's own successful local `setCurrent` calls — never by an incoming fresh `summary` prop from any other cause (a concurrent regenerate, a cron run, or any future feature on this page that calls `router.refresh()`). The "View history" dialog has no such staleness, creating a directly-visible self-contradiction for the user.

## Suggested Owner
Frontend Lead / Feature owner of `src/features/dashboard/components/monthly-summary-card.tsx` — same fix boundary as the Spending Insights period bug (resync `current` to `summary` on prop change, e.g. via `useEffect`, or eliminate the redundant local-state mirror entirely and derive display state from props alone, updating only via `router.refresh()`).
