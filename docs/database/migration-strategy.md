## Ongoing process (binding from Phase 2 onward)
1. Database Architect authors schema changes in `prisma/schema.prisma` only after the relevant Product Owner spec and Solution Architect design exist for that phase's domain (per Architecture.md's role boundaries) — never speculatively.
2. Every migration is generated via `prisma migrate dev --name <descriptive-name>` and committed alongside the schema change, never hand-edited SQL except for three narrow, deliberate exceptions: (a) genuinely irreversible data backfills, (b) a database constraint Prisma's schema DSL has no syntax to express at all — the concrete example on record is a partial/conditional unique index (`CREATE UNIQUE INDEX ... WHERE ...`), which Prisma has no `@@unique` equivalent for — or (c) a one-time deploy-time seed a brand-new table needs before its first real application consumer runs (the concrete example on record: `system_category_template`/`feature_flag`'s seed rows, `20260729145632_phase_4c_calendar_customization_admin`, below). Exceptions (b)/(c) are generated via `prisma migrate dev --create-only` (or, if `migrate dev` itself is blocked — see that same Phase 4c entry below for why it was blocked here — via `prisma migrate diff` against the live datasource, producing the equivalent DDL-only SQL by hand) and then hand-editing that file's `migration.sql` to append the raw SQL, before applying it — see `category_suggestion_pending_partial_unique_index` above for the first applied instance of exception (b), and the Phase 4c entry below for the first applied instance of exception (c). All three exceptions remain rare, reviewed case-by-case, and never a substitute for reaching for Prisma's normal generated-migration flow first.
2a. **If `prisma migrate dev` refuses to proceed and asks to reset the database**, stop and diagnose before ever running `migrate reset` — that command drops and recreates the entire schema, discarding all data. The concrete case on record (Phase 4c): a prior migration's `migration.sql` had its *comment* hand-edited after being applied (permitted — the executable SQL itself was untouched), which changes that file's checksum relative to what `_prisma_migrations` recorded at apply time; `migrate dev`'s own drift-detection step treats this as reason enough to want a full reset, even though the actual database schema was never out of sync with `prisma/schema.prisma` (confirmed via `prisma migrate status`, which reported "up to date" throughout). The safe alternative used here: generate the desired DDL via `prisma migrate diff --from-url <DATABASE_URL> --to-schema-datamodel prisma/schema.prisma --script`, hand-author the new migration folder from that output (plus any DataMigration blocks per exception (c) above), and apply it with `prisma migrate deploy` — which applies pending migrations without `migrate dev`'s shadow-database drift comparison. Always confirm `DATABASE_URL` points at a dev/non-production database before running any of this (per this document's own standing caution and the release checklist) — never destructive, but still real infrastructure.
3. **Additive-first**: new columns are nullable or have defaults so existing rows remain valid without a backfill step blocking deploy. Making a column required happens in a follow-up migration after a backfill, not the same migration that introduces it.
4. **Renames are two migrations**, not one: add the new column, backfill/dual-write, then drop the old column in a later migration — never a single `ALTER ... RENAME` on a table that might have production data by Phase 2+.
5. Destructive migrations (drop column/table) require Release Manager sign-off per the release checklist — they are irreversible in production.

## Seed data
- `prisma/seed.ts` is dev/demo-only (creates a `demo@financeos.local` user). It is never run against production. `DEFAULT_CATEGORIES` lives in `src/features/categories/default-categories.ts` (a side-effect-free module `prisma/seed.ts` imports from, not the other way around, since `prisma/seed.ts`'s `main()` runs unconditionally at import time). Production users get their default categories created automatically at signup via a Better Auth `databaseHooks.user.create.after` hook in `src/lib/auth.ts`, which imports the same `DEFAULT_CATEGORIES` list.
- **Phase 3a addition**: `prisma/seed.ts` now also creates one linked Debt (Credit Card, exercising `accountId` set) and one standalone Debt (Student Loan, exercising `accountId: null` — the no-Account-counterpart case), one Investment container Account with one Holding plus a `HoldingValueHistoryEntry` and a `DividendEntry`, and one Recurring Income `IncomeStream` with one generated `IncomeOccurrence`. This is enough to exercise every new model at least once in local/demo development; it is not exhaustive fixture data for payoff-math.ts/allocation-percentage correctness testing, which is Integration Test Engineer's responsibility against dedicated test fixtures, not this dev seed script's job.
- **Phase 3b addition**: `prisma/seed.ts` now also creates one `FinancialGoal` per type — `DEBT_PAYOFF` linked to the Student Loan Debt seeded above (exercising `linkedDebtId`/`startingBalance`), `NET_WORTH_SAVINGS_TARGET` against the `TOTAL_NET_WORTH` basis (exercising `targetAmount`/`measurementBasis`), and `SAVINGS_RATE_TARGET` (exercising `targetPercent`) — plus one `DismissedSubscriptionMerchant` row. The `ACCOUNT_SUBSET` measurement basis and its `FinancialGoalAccount` join-table row are deliberately not seeded here (a second Net Worth/Savings Target goal purely to exercise a join row doesn't earn its place in a minimal dev seed); that case belongs to Integration Test Engineer's dedicated fixtures instead.
- **Phase 4a addition**: `prisma/seed.ts` now also creates one row per new AI-features model — a second, Uncategorized demo transaction with a `PENDING`/`AUTOMATIC` `CategorySuggestion` against it (exercising `suggestedCategoryId`/`source`/`status`/`confidence`/`generatorModel`); a `BudgetAdvisorCache` row for the current month; a `MonthlySummary` row for a fully-closed prior month with a narrative present (the "generation succeeded" case); a `SpendingInsightsCache` row; and a `FinancialHealthScoreSnapshot` row with all four components defined and a narrative present. Deliberately not exhaustive — the `REJECTED`/`ACCEPTED` `CategorySuggestion` states, a failed-generation (`narrative: null`) row for any of the three AI-content models, and an undefined-component `FinancialHealthScoreSnapshot` are Integration Test Engineer's dedicated fixture concerns, the same "exercise every new model at least once, not every state" standard already applied above. No `lib/ai/` call happens anywhere in this script — every generated-content field is static seed literal text, so the seed script has no network/API-key dependency.
- **Phase 4c note (deliberately no `prisma/seed.ts` change in this pass)**: `DEFAULT_CATEGORIES`/`src/features/categories/default-categories.ts` is left in place, untouched, exactly per `phase-4c-technical-design.md` §4.3's explicit instruction — `prisma/seed.ts` is its one remaining consumer (production signups now read `SystemCategoryTemplate` instead, via `features/categories/server/template.ts`'s `getSystemCategoryTemplate()`, wired into `lib/auth.ts`'s signup hook). Whether to eventually retire `DEFAULT_CATEGORIES` and point `prisma/seed.ts` at `SystemCategoryTemplate` too is a future Database Architect/Backend Engineer call, not required for Admin's Manage Categories capability to function. None of this pass's new models (`UserPreference`, `DashboardCardPreference`, `SystemCategoryTemplate`, `ReportGenerationEvent`, `FeatureFlag`, `AdminActionLog`) are exercised by `prisma/seed.ts` in this dispatch — extending that script is left to whichever future dispatch implements the actual Settings/Admin features against this schema (the same "schema pass first, seed-script/feature-code extension later" split already applied to `ReasoningModelCallLog`'s own eventual `advisor.ts`/`monthly-summary.ts` wiring above).
